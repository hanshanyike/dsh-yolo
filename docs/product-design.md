## 一、背景与问题

### 1.1 原型已验证什么

Keeper（M0–M7）与 Organizer（M8）两级已经交付了一个能跑的闭环：LLM 从对话中提取计划项，SQLite/FTS5 长期存储，到期提醒，侧边栏看板展示，用户可以在看板上点掉或推迟任务，也可以在对话里用自然语言处理提醒。175 个测试、CI、npm 包齐备。

自用两周后的真实体验暴露了四个结构性问题：

| # | 问题 | 证据 |
|---|---|---|
| P1 | **提醒打扰工作会话** | 到期提醒通过 `agent.followup()` 注入最近的工作会话，正在写代码时被插入一条「⏰ 提醒」 |
| P2 | **没有自己的对话面** | 想问「我这周干了什么」或随手记一件事，没有自然入口——工作会话里问会污染上下文 |
| P3 | **不知道当天干了什么** | 每天与 AI 的会话有十几个，事后无法回答「今天究竟推进了哪些事、各自到哪了」；AI 帮人完成更多事，但事情的总量超出了人的心智负担 |
| P4 | **看板是静态投影** | 五段式列表按数据类型（todos/goals/milestones/preferences/events）组织而非按时间与当下组织；无筛选、无编辑、无「今日」概念 |

其中 P3 是本次设计最重要的输入：它把根叙事补全了。VISION 说的「跨会话会忘」（意图连续性断裂）是问题的一半——YOLO 帮你**记**；P3 说的「跨会话太多会晕」（全局视野丢失）是另一半——YOLO 帮你**盘点**。产品因此有两个核心答案：**「什么该做了」（提醒与聚焦）** 与 **「今天干了什么」（台账与简报）**。

### 1.2 外部调研的三条启示

- **ChatGPT Tasks 的形态可参照、坑要避开**：独立任务页 + 到点推送 + 点通知回到任务自己的线程查看与回复，这个「任务有自己的投递面」模型与 YOLO 方向一致；其公认缺陷（任务与聊天线程强耦合、删线程毁任务、上下文隔离）反向印证了 YOLO 的设计——计划数据活在 storage 而非任何会话线程里，会话只是投影视图。
- **Copilot UX 准则的「对话优先」要按场景修正**：通用 agent 准则是聊天为主、工作区辅助。但 YOLO 的用户打开面板的第一诉求是**看状态**而非**说话**，因此本次设计把看板放主位、对话做成锚定看板内容的侧栏——这是对通用范式的有意偏离，依据是自用场景的真实诉求排序。
- **Things 的「按当下与时间组织」**：成熟任务管理工具的默认视图都是时间轴（今天/即将）而非数据类型清单，与 P4 的整改方向一致。

## 二、目标用户与关键场景

**目标用户**：本人（重度 deepseek-harness 用户，多项目并行、每天十几个 AI 会话）。产品化（onboarding、默认配置打磨、商店分发）不在本期范围，但数据格式与配置项为未来开放留口子。

四个关键场景（时刻）：

| 时刻 | 场景 | 产品应答 |
|---|---|---|
| 早晨开工 | 打开电脑，想知道今天该关注什么 | 看板默认视图 + 早报通知卡（今日到期、逾期、昨日遗留） |
| 白天工作 | 沉浸在某个工作会话写代码 | 工作会话 100% 静默；到期提醒只在 YOLO 侧边栏角标上出现；随手记事走 YOLO 面板 |
| 收工回顾 | 想知道今天干了什么、还挂着什么 | 晚报通知卡 + 今日台账（事件级 + 会话来源标注） |
| 随时盘点 | 想看全局、改计划、追问细节 | 看板筛选与行内编辑；点「聊一聊」展开侧栏对话，边看边聊、就地生效 |

## 三、产品全景蓝图

### 3.1 产品表面：三件套

```
┌─────────────────────────────────────────────────────────────┐
│  ① 看板（默认面·状态投影）                                     │
│     「什么该做了」+「今天干了什么」                              │
│     筛选 / 今日聚焦 / 任务行 / 台账 / 通知卡                     │
├─────────────────────────────────────────────────────────────┤
│  ② YOLO 对话（意图入口）                                       │
│     当前工作区常驻线程：查询 / 记录 / 改计划 / 出简报 / 答提醒      │
│     事项线程：每次从判断或处理面板进入的全新锚定对话               │
├─────────────────────────────────────────────────────────────┤
│  ③ 后台记忆引擎（不可见·事实源）                                 │
│     提取（turn 级 LLM）· 存储（SQLite+FTS5+快照）· 召回 · 调度   │
└─────────────────────────────────────────────────────────────┘
        统一交互语法：卡片 → 聊一聊 → 侧栏对话 → 就地生效
```

三个部件的关系：**引擎是唯一事实源**（计划数据在 storage，不在任何会话线程里）；**看板是状态的投影视图**；**会话是意图的入口**。提醒、简报、任务在看板上都是卡片，所有深入交互都是「点卡片 → 聊一聊 → 对话 → 数据更新 → 看板即时刷新」。一条语法走天下。

### 3.2 能力弧线映射

| 愿景弧线 | 版本 | 状态 |
|---|---|---|
| Keeper · 记得 | 0.1（M0–M7） | 已交付 |

## 四、信息架构与交互设计

### 4.1 布局与一级导航

侧边栏底部保留 YOLO 按钮（唯一常驻入口，兼角标触达点）；点击打开助手看板。头部把「对话」作为主操作、通知作为次操作，刷新、主题、目标与台账等低频入口收进「更多」。

340px 常驻侧栏与宽屏使用同一套信息架构，一级导航固定为：

1. **今天**：默认面，回答“现在最值得回应什么”；
2. **即将**：查看未来安排与其他开放事项；
3. **已完成**：分别查看已完成、已取消事项，并可重新打开。

「目标与里程碑」「今日台账」通过更多菜单或页面内上下文入口进入，不与今日处理争夺一级导航。宽度增加只改变承载方式，不增加另一套导航语义。

### 4.2 “今天”与唯一助手判断

“今天”按固定顺序阅读：日期与概览 → 快速记录 → **助手判断（若有）** → 需要关注 → 今天 → 今天进展 → 可选收束。

- 同时最多显示一个助手判断；没有达到阈值的候选时不显示空壳卡；
- 判断只基于截止时间、提醒、优先级、推迟次数、停滞与里程碑等可验证事实，由服务端确定性排序；
- 判断卡展示短结论、1–3 条证据、来源和处理入口；首次完整展示，服务端记录已看后复读为紧凑态；
- 主判断事项从下方列表去重；退出重点后按当前状态回到“需要关注”或“今天”；
- 快速记录继续不经 LLM 直写，默认今天到期。

### 4.3 事项处理面板与学习回执

事项行的「处理」和判断卡的「更多处理」进入同一处理面板，顺序固定为：事项与工作区 → 判断依据 → 来源 → 快速处理 → 助手将记录的变化 → 编辑事项 → 危险操作。

- 快速处理包含完成、推迟、再提醒与“和助手讨论”；编辑支持标题、截止时间、优先级和里程碑；
- 完成保留 4 秒撤销；取消属于显式危险操作；所有动作走统一 actions 路径并写审计；
- 界面只展示服务端返回的学习回执，不根据点击自行推断“助手学会了”；
- 单次完成、推迟或忽略不会静默生成长期偏好。当前回执只陈述实际状态、排期、提醒或判断反馈变化及其作用范围。

### 4.4 常驻对话与事项对话

- **常驻对话**：头部「对话」进入当前工作区的 `yolo-w-*` 常驻线程，跨打开保留历史，可查询、记录、改计划和处理提醒；
- **事项对话**：从判断、事项行或处理面板进入，每次创建全新的 `yolo-a-*` 锚定线程；只携带事项标题、id、所属工作区和必要上下文，不继承常驻历史；
- 两类对话都使用 dsh 当前模型选择；计划事实仍在 storage，对话只是意图入口；
- 工作会话始终静默，不接收 YOLO 的提醒、简报或追问。

### 4.5 聚合、部分数据与刷新

看板始终聚合所有已知工作区，不提供“当前/全部”切换。每一行携带稳定工作区归属，完成、推迟、编辑、取消和重新打开按该行 `scope_cwd` 路由，因此聚合不是只读视图。

某个工作区读取失败时保留其他成功数据并显示“部分工作区暂不可用”；在 `partial` 状态下不声称当前判断代表全局最重要事项。打开看板只加载一次，动作和手动刷新才重新拉取全量数据；关闭看板后角标仍独立轻量更新。

### 4.6 提醒与简报投递链路

```
到期检测（scheduler 轮询）
   → 投递到 YOLO 会话（followup yolo session）         ← 不再触碰工作会话
   → 面板打开中: 看板通知卡（标题 + 快捷操作）
     面板未打开: 侧边栏按钮角标（未处理计数）
   → 用户处理: 看板快捷操作 / 侧栏对话回复（"已完成""推迟到明天"）
   → storage 状态流转 + 审计事件 → 角标/通知卡清除
```

- **工作会话 100% 静默**（D7）：任何提醒、简报、追问都不注入工作会话，无例外。
- **早晚报**（D12）：可配置时间与开关；早报 = 今日到期 + 逾期 + 昨日遗留 + 目标进展变化；晚报 = 今日完成清单 + 新增记录 + 还挂着的事。呈现为看板顶部通知卡，点「聊一聊」带着简报上下文展开对话，可追问。
- **系统级通知**（面板外推送）本期不做，列为开放问题。

### 4.7 编辑深度

| 对象 | 可编辑字段 | 方式 |
|---|---|---|
| 待办 | 标题、截止日、优先级、里程碑归属、删除 | 行内原地编辑；改期用日期选择；删除需确认并写审计事件 |
| 里程碑 | 标题、状态、删除 | 折叠区内编辑 |
| 目标 | 标题、删除 | 折叠区内编辑 |
| 目标进度 | **不可手动编辑** | 进度只能来自对话陈述或提取；直接在看板改数容易产生无法追溯的「假进度」 |

（D15：编辑边界经讨论确认。）

## 五、版本交付演进

### v0.3.3 · 助手判断优先（当前，未发布）

本批在 v0.3.0 面板闭环上完成 Dashboard v2：唯一确定性判断、三项一级导航、事项处理面板、服务端学习回执、全工作区可操作聚合、常驻/事项对话隔离，以及部分工作区失败提示。发布、tag 与版本推进仍需单独授权。

### v0.3.0 · 面板 1.0 历史基线（已交付）

范围决策 D17：五项全包，形成后续 v0.3.3 重构所依赖的提醒、台账、简报、筛选编辑与面板基础。以下 A–E 作为历史需求与回归背景保留。

### A. 面板重构

**需求**：侧边栏按钮入口 → 全宽 YOLO 面板；看板 Tab 默认 + 侧栏对话可展开 + 对话 Tab；快速记一条输入框。

**要点**：重构 `client/` 的 UI bundle——现侧边栏 drawer（`YoloSidebarDashboard`）升级为面板级视图；侧栏对话为看板 Tab 内的子组件，常态收起、点「聊一聊」或对话开关展开、Esc/点外部收起；快速记一条直写 storage 不经 LLM。

**验收**：按第八节测试场景 TA-1～TA-6 过测，全部通过即验收。

**架构影响**：client bundle 大改；**宿主「与常规会话同宽」面板的承载方式需先行调研**（见开放问题 #1，实现第一风险项）。

### B. 提醒改道

**需求**：提醒由 YOLO 自己投递，工作会话 100% 静默。

**要点**：reminder 插件的投递目标从「最近工作会话 followup」改为「YOLO 常驻会话」；YOLO 会话生命周期管理（启动创建、重启恢复、回放未处理提醒）；侧边栏按钮角标（未处理计数）。

**验收**：按第八节测试场景 TB-1～TB-6 过测，全部通过即验收（TB-1 为核心场景）。

**架构影响**：reminder 插件投递逻辑重写；新增 YOLO 会话管理模块；pending reminder 队列复用。

### C. 今日台账

**需求**：事件级台账 + 会话来源标注。

**要点**：`events` 表补 `session_id` 归属（issue-timeline-session-attribution.md 已定位的缺口，需 schema 迁移）；每个会话维护一句话摘要（turn-end 提取时顺手生成/更新），作为来源徽标文案；台账视图按日聚合渲染。

**验收**：按第八节测试场景 TC-1～TC-6 过测，全部通过即验收。

**架构影响**：schema 迁移（`events.session_id`）；extract 模块增加会话摘要输出；dashboard API 扩展台账数据。

### D. 早晚报

**需求**：定时简报任务，通知卡呈现，可追问。

**要点**：复用 reminder scheduler 基建增加定时任务类型；配置项 `brief.morningTime` / `brief.eveningTime` / 开关（默认开，时间默认 09:00 / 21:00，可关）；简报内容按 4.6 要素生成（一次 LLM 调用）；通知卡支持「聊一聊」锚定简报全文。

**验收**：按第八节测试场景 TD-1～TD-6 过测，全部通过即验收。

**架构影响**：scheduler 扩展；新增简报生成 prompt；LLM 调用建议错峰（沿用既有 off-peak 偏好）。

### E. 看板筛选与编辑

**需求**：预设 Tab + 组合筛选；行内编辑。

**要点**：筛选条件（状态/到期/里程碑/关键词）可独立生效可组合；编辑按 4.7 边界实现，全部写审计事件；编辑后 SQLite 与 Markdown 快照同步。

**验收**：按第八节测试场景 TE-1～TE-8 过测，全部通过即验收。

**架构影响**：dashboard API 增加查询参数；actions API 增加 update/delete 动作；前端表格组件重构。

## 七、明确不做与边界

- **不做**目标进度手动编辑（防「假进度」，D15）；
- **不把**偏好放进看板界面（偏好是引擎的记忆，D14）；
- **不做**工作区切换器：助手看板固定聚合所有已知工作区，但保留逐行归属、权限边界和部分失败提示；
- **不从一次点击静默学习**长期偏好，也不在无服务端回执时声称“已经记住”；
- **不做**系统级推送通知（面板外触达仅角标；系统通知列开放问题 #2）;
- **不做**多人协作、分享、云端同步（与「本地优先、私密内敛」冲突）;
- **不做**任务管理器级别的复杂功能（甘特图、依赖关系、子任务树）——YOLO 聚焦于从对话中整理事项、提醒和记录变化，不做第二个 Todoist。

## 八、测试场景与验收标准

验收以**功能正确、判断可信和跨工作区动作安全**为准。下面 TA–TE 保留 v0.3.0 历史回归语义；当前 v0.3.3 的准入以“Dashboard v2（TV2）”和 [重构 PRD 的 Definition of Done](prd-assistant-dashboard-rearchitecture.md#24-definition-of-done) 为准。

### Dashboard v2（TV2）

| ID | 场景 | 期望 |
|---|---|---|
| TV2-1 | 打开“今天” | 固定阅读顺序成立；合格候选最多一个助手判断，重点事项不在下方重复 |
| TV2-2 | 首读与复读 | 首次展示完整证据与来源；服务端记录 seen 后刷新为紧凑态，可重新展开 |
| TV2-3 | 处理与回执 | 完成、推迟、再提醒、忽略与反馈走统一动作；只展示服务端 learning receipt，完成可在 4 秒内撤销 |
| TV2-4 | 导航与 340px | 一级仅“今天 / 即将 / 已完成”；目标、台账、刷新、主题进入 More 或上下文入口 |
| TV2-5 | 聚合动作 | 所有工作区行均显示归属，并按 `scope_cwd` 在所属工作区完成动作；未知 scope 被拒绝 |
| TV2-6 | 对话隔离 | 全局对话复用常驻线程；每次事项讨论为全新锚定线程，不出现常驻历史 |
| TV2-7 | 部分数据 | 单个工作区失败不拖垮整页；页面明确提示 partial，判断不冒充全局最重要事项 |
