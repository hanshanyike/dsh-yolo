# YOLO 助手看板原型与产品设计记录

> 状态：已评审并作为 v0.4.0 首版实现依据
>
> 中文口号：**交代一次，持续跟进。**
>
> English slogan: *Say it once. Keep it on track.*

本文件把曾经用于评审的产品原型、交互决策和当前实现边界集中保存。它回答的是“用户看到什么、为什么这样组织、上下文怎样展开”，而不是代码如何实现。跨模块的数据和接口契约见[整体架构](../architecture/overview.md)，长期产品边界见[产品愿景](../VISION.md)。

可点击的单文件视觉原型：[打开助手看板 HTML 原型](assistant-dashboard-prototype.html)。原型用于理解信息层级和状态变化，不代表页面中的示例数据是真实用户数据。

## 1. 产品定位

YOLO 是面向工作与生活的个人智能助理。当前版本连接人和多个 AI 工作会话：接住用户在会话中做出的交代，形成可追踪的安排，并在合适的时间把需要回应的事情带回注意范围。长期方向是在用户授权下连接用户与 Agent，持续维护事项、决定、约束、进度和结果。

核心价值链是：

```text
交代 → 识别需要持续跟进的安排 → 保存来源与状态 → 在合适时机提醒 → 用户决定下一步
```

产品的第一版重点不是“拥有更多功能”，而是让用户相信三件事：

1. 说过的明确安排不会轻易丢失；
2. 看板中的每一项都能解释为什么出现、来自哪里；
3. 提醒不会闯入正在进行的工作会话，也不会替用户擅自行动。

待办是当前最先落地的一类管理对象，不是产品的最终边界。长期可管理的对象还包括目标、决定、阻塞、等待、来源证据和经过授权的 Agent 任务；它们必须共享同一份可追踪状态，而不是各自建立独立的记忆或执行系统。

## 2. 设计原则

### 2.1 管理而非代办

YOLO 管理承诺、时间、状态和提醒。完成、推迟、取消、讨论和修正都由用户确认；执行代码、发送消息、改变外部系统不属于首版默认权限。

### 2.2 一个事实源，多种视图

计划数据保存在本地存储中。首页、计划、历史、提醒卡和对话上下文都是同一份事实的不同投影，不在前端各自维护一套“看起来正确”的状态。

### 2.3 证据先于解释

每一项由会话整理出的安排优先显示来源会话、有限摘录、工作区和可用轮次信息。模型可以整理表达，但不能凭空制造来源或进度。

### 2.4 低打扰、可恢复

提醒进入 YOLO 自己的通知和常驻线程，不注入普通工作会话。关闭面板、切换宽度、暂时离开上下文后，页面、草稿、讨论轮次和焦点都应尽量恢复。

### 2.5 适配宿主，而不是假设独立应用

deepseek-harness 的侧栏和可用主区域是不确定的。首版不使用固定的“宽视口三栏”假设，而是根据 YOLO 实际可用宽度决定是否并排显示一个上下文区。

宿主侧栏是唯一的全局导航。YOLO 从宿主侧栏右缘展开，在内部只保留顶部页面切换、一个主内容面和最多一个上下文区；上下文区在整体助手对话、事项讨论、事项详情、来源预览和 Agent 任务详情之间互斥切换。

## 3. 信息架构

首版只有三个一级页面：

| 页面 | 用户问题 | 内容边界 |
|---|---|---|
| 首页 | 现在最需要回应什么？ | 一个首要判断、需要处理的安排、今天、接下来、最近变化摘要 |
| 计划 | 所有开放安排如何组织？ | 今天、接下来、目标、全部；筛选只影响计划页面 |
| 历史 | 已经发生了什么，这件事如何走到现在？ | 按时间回顾变化，或按事项查看完整演进；状态筛选包含进行中、已完成、已取消与已合并 |

“进展”不再是一级页面。它的语义被拆为两部分：当前需要回应的事项归入首页和计划，已经发生的变化归入历史。历史内部提供“按时间 / 按事项”两个正交投影；“已结束”是按事项的状态筛选，不再与时间线并列成展示模式。这样用户既能回答“最近发生了什么”，也能回答“一件事为什么成为现在这样”。

按事项分组必须使用工作区、主体类型和稳定 ID，不得按标题猜测。同名事项、改名事项和跨工作区事项保持独立；旧事件缺少稳定主体时只在按时间视图诚实显示为早期记录。

“Agent 任务”属于后续协同阶段。本首版不显示该入口，也不暗示 YOLO 已经拥有自动执行权限。

## 4. 首页原型

首页的阅读顺序是固定的：

```text
日期与结论
  ↓
快速记录
  ↓
首要判断（最多一项）
  ↓
需要处理 / 今天 / 接下来
  ↓
最近变化
```

### 4.1 顶部结论

顶部不是抽象的“仪表盘分数”，而是一句面向行动的结论，例如“今天有 2 件事需要你处理”。当没有开放安排时，结论明确告诉用户今天没有需要处理的事，并保留“和助手聊聊”入口。

### 4.2 首要判断

服务端可以从所有工作区的开放事项中选出最多一项当前最值得回应的判断。首读显示“为什么现在”、结构化证据和来源；再次查看可以收缩为简洁版本。首要判断与下面的任务列表不重复。

### 4.3 次要安排与压力控制

需要处理的事项、今天到期的事项和有明确日期的后续事项使用同一行模型。普通状态下分组展示；当首要判断加上次要安排达到高压力阈值时，只突出首要判断，其余通过“查看其余安排”一次展开。无日期的普通积压不为了填满首页而出现，但仍可在计划的“全部”中找到。

### 4.4 最近变化

首页只显示少量用户可理解的变化摘要，并提供进入历史的入口。提醒扫描、抽取完成、已读标记等内部事件不会伪装成产品进展。

## 5. 单一上下文模型

面板同一时间只存在一个前景上下文：

| 上下文 | 用途 | 宽度足够时 | 宽度不足时 |
|---|---|---|---|
| 整体助手对话 | 询问、记录、讨论多个安排 | 右侧 340px | 替换看板进入 focus |
| 事项讨论 | 只围绕某一安排继续交流 | 右侧 340px | 替换看板进入 focus |
| 事项详情 | 查看和修改结构化字段 | 右侧 340px | 替换看板进入 focus |
| 来源预览 | 查看来源证据、打开原会话 | 右侧 340px | 替换看板进入 focus |

这里的“一个上下文”是状态约束，不是强制三栏布局。看板、宿主侧栏和上下文的实际尺寸由宿主让出的空间决定；上下文之间互相替换，不会同时叠出详情、来源和聊天三层面板。

### 5.1 打开、返回与关闭

```text
看板触发器
  → 打开前景上下文
  → 返回上一层：恢复来源前的上下文
  → 关闭上下文：回到原页面与原触发器
  → 关闭面板：回到宿主，同时保留可恢复的导航状态
```

来源预览从事项详情打开时，返回应回到详情而不是首页；从计划行打开时，返回应回到原计划行。键盘焦点优先回到仍可见的精确触发器，触发器失效时才按事项行、页面主动作逐级降级。

### 5.2 对话边界

整体助手对话与事项讨论使用不同的临时上下文。事项 A、事项 B 和整体对话不互相混入历史；隐藏上下文后再次打开仍延续同一讨论 episode，明确结束讨论后才创建新的 episode。

Agent 任务不是事项讨论的别名。它必须有独立的任务目标、授权范围、执行状态、结果和验收状态；Agent 会话只是一次执行载体，Agent 报告完成也不自动代表关联安排已经完成。

## 6. 来源、提醒与动作

### 6.1 来源证据

来源预览优先显示：工作区、来源类型、会话名称、有限用户原话摘录、记录时间和可选轮次。手动记录、工具来源、早期旧数据在能力不足时明确降级，不显示虚假的“打开原会话”。

### 6.2 提醒

提醒有两个触达面：

- YOLO 侧栏角标，表示尚未查看的新通知投递数量；
- 首页事项中的提醒正文与处理入口。

同一事项的多条提醒在首页折叠为一项，角标仍保持精确计数。“知道了”只处理通知，不会把事项误标为完成。新提醒刷新通知数据，但不抢走用户正在查看的详情、来源或对话。

### 6.3 统一动作

完成、推迟、取消、重新打开、再次提醒、快速记录和讨论入口都通过统一动作路径执行。动作结果应同时反映在事项状态、审计记录、提醒计数和页面投影中。

## 7. 响应式与宿主关系

设计只约定组件最小可用宽度，不约定浏览器视口断点：

- 面板可用宽度足够：看板与一个 340px 上下文并排；
- 面板可用宽度不足：上下文进入 focus，隐藏看板而不是挤出横向滚动；
- 宿主侧栏展开或收起：只重新计算可用空间，不能丢失草稿、请求、讨论 episode 或来源位置；
- 紧凑面板：标题、按钮、表单和证据文本保持可读，所有交互控件仍可键盘访问。
- 宽度阈值由主内容最低可用宽度、上下文宽度和间距共同推导，不把 `960px` 视为固定产品契约。

## 8. 可访问性契约

- 一级页面使用真正的 tab 语义、方向键和 Home/End 导航；
- focus 上下文使用 dialog 语义，背景不可达；split 上下文不是 modal，主面仍可操作；
- Tab 和 Shift+Tab 在实际可见、可聚焦元素之间循环，不把隐藏控件算入候选；
- 返回或关闭后恢复原触发器焦点，失效时使用明确的安全回退；
- 动态提醒使用单一 polite live region，不因刷新重复读同一消息；
- reduced-motion 下取消动画和过渡，但不改变信息层级和操作路径。

## 9. 原型与实现的关系

HTML 原型保留的是设计语义和状态关系，示例数据、颜色和文案可以在实现中继续迭代。当前实现已经落地的对应关系如下：

| 原型决策 | 当前实现入口 |
|---|---|
| 三个一级页面 | `client/panel/PageTabs.tsx` |
| 首页统一投影 | `src/shared/dashboard-surfaces.ts`、`client/panel/v2/TodaySurface.tsx` |
| 单一前景与响应式 | `client/panel/navigation.ts`、`client/panel/YoloPanel.tsx` |
| 来源预览与会话跳转 | `client/panel/ForegroundContext.tsx` |
| 事项详情和动作 | `client/panel/v2/TaskActionPanel.tsx` |
| 本地数据、来源字段与迁移 | `src/storage/`、`src/shared/dashboard.ts` |

若后续产品讨论改变一级页面、前景生命周期、来源证据或提醒边界，应先更新本文件与 HTML 原型，再更新实现契约和验收矩阵。这样原型不会再次变成只存在于一次聊天中的隐含决策。

## 10. 后续产品方向（未实现）

本节记录已确认的产品方向，不代表当前版本已经提供这些能力。

### 10.1 统一的产品对象

对外继续使用“事项”这个普通词。事项可以是待办、目标、决定、阻塞、等待或 Agent 任务，但都应具备明确的范围、来源、当前状态和下一检查点。用户看到的是事项；内部实现可将其拆为证据、当前上下文、计划和执行工作四层。

```text
证据：会话、用户原话、工具结果、Agent 产物
  ↓
当前上下文：有效事实、约束、依赖和冲突
  ↓
计划：目标、里程碑、事项和提醒规则
  ↓
执行工作：人或 Agent 的一次受控执行尝试
```

计划表达“用户希望发生什么”，执行工作表达“某次尝试做了什么”。执行成功不自动等于计划完成，结果需要验证或用户验收。

### 10.2 Agent 任务

“Agent 任务”是后续协同阶段的正式产品名称；“委托给 Agent”是创建动作。一个 Agent 任务至少需要关联目标或事项、执行 Agent、授权范围、完成标准、状态、结果和验收记录。

默认原则是：人类保有目标和最终责任，Agent 负责受限执行；等待授权、受阻、失败和待验收的 Agent 任务可以进入首页，需要用户处理时才提升注意级别；普通运行状态不制造高频提醒。

### 10.3 演进边界

后续先验证跨会话连续性和状态可信度，再增加个人范围、冲突识别、Agent 观察、授权委托和结果验收。任何新增能力都必须增强“交代一次，持续跟进”的闭环，并保持来源可查、范围隔离、权限明确和普通工作会话安静。
