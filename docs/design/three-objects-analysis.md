# 事项 / 里程碑 / 目标：概念边界与可理解性分析

> **触发问题**：「里程碑和目标还有计划有什么区别，是什么设计理念和设计哲学，用户能否直接理解？」
>
> **证据口径**：`docs/VISION.md`、`docs/design/goal-management.md`、`src/**`（数据模型与看板投影）、
> `client/**`（界面文案与入口），以及本机 3 个真实工作区存储（不含 `[E2E]` 夹具）的实际内容。
> 文中「事实」与「判断」分开标注；判断均可回溯到本文第 5、9 节的证据。

---

## 0. 结论速览

1. **设计上的三层是清楚的**：事项＝行动，里程碑＝阶段**结果**，目标＝长期结果。三者不是同一层级的三个标签，
   而是三种不同的「证明方式」：事情做了（事项）／某个阶段成立了（里程碑）／最终结果达成了（目标）。
2. **但产品上只有两个自明层级**：能提醒的最小行动（事项）和长期结果（目标）。里程碑是「目标之下的阶段检查点」，
   却被做成了目标页里的一等对象，而**没有任何地方解释它是什么**。
3. **「计划」根本不是实体**，它是页面名——开放事项按到期日的划分（全部／今天／接下来／未排期）。
   中文语感里「计划」天然包含目标与里程碑（用户会说「我的计划是这个季度发布 0.5.0」），
   于是「计划 vs 目标」的困惑是**命名撞车**，不是概念不清。
4. **判定：今天的新用户无法直接理解三者区别。** 三条硬证据：里程碑没有独立入口（§3）、
   关系数据算了但界面不用（§2）、抽取把「行动」写成「里程碑」（§5）。§7 给出分档修复建议，§8 给出可测的验收信号。

## 1. 设计理念（事实源）

`docs/design/goal-management.md` 已经把哲学写得很完整，摘要如下（引号内为原文，行号为该文件当前行号）：

| 对象 | 回答的问题（原文） | 时间尺度 | 能否独立存在 | 提醒方式 | 状态 |
|---|---|---|---|---|---|
| **事项** | 「现在或随后要做的一件具体事情」（L33） | 一次行动 | 能（很多承诺不属于任何目标） | 到期提醒 | pending / in_progress / done / cancelled |
| **里程碑** | 「我们到了哪个阶段？什么阶段性结果已经成立？」（L51） | 一个阶段 | 能（「外部阶段、独立项目检查点和一次性验收可以独立记录」，L98） | 阶段检查（低频） | planned / active / done / abandoned |
| **目标** | 「一段时间内希望达成的最终结果」（L75） | 数天至数周以上 | 能（可先作为**待确认**目标，L19） | 回顾（由回顾日期或明显状态变化触发，L259） | candidate / active / paused / achieved / abandoned |

四条关键设计承诺（会被下面的真实数据逐条对照）：

- **不是父子任务树**：「目标不是任务树的根节点，里程碑也不是事项容器」（L102）；
  「一个里程碑事项必须属于目标」被明确列为**不推荐**（L98）。
- **里程碑关心结果，不是动作**：「'准备内部评审材料'是事项；'内部评审完成'才是里程碑」（L61）。
- **不用完成数推导进度**：反例三「按事项完成数自动计算目标进度」被拒绝（L491）；
  目标达成仍需用户确认（L297）。
- **活跃目标必须有下一步**；只有等待／阻塞且有原因时才可以没有下一步（L18、L309）。

一句话概括这套哲学：**YOLO 管理的是「承诺的连续性」，不是「任务的层级」。** 它不替你拆解，
只负责让「一个结果 → 当前阶段 → 下一步」这条链不断掉。

> ⚠️ 文档漂移：该文 §5.2（L395）仍写「计划 → 目标会展示……」，而 `013aa17` 之后
> **目标已是一级入口**（`client/panel/PageTabs.tsx` 的 `PAGES`）。设计文档这一节需要随代码更新。

## 2. 数据模型事实

| 表 / 关系 | 承载对象 | 说明 |
|---|---|---|
| `todos` | 事项 | `due_at`、`priority`、`status`、`milestone_id`（**遗留**：事项「支撑／对应」哪个阶段） |
| `milestones` | 里程碑 | `status`、`target_date` |
| `goals` | 目标 | `completion_criteria`、`progress`、`progress_source`、`next_todo_id`、`next_review_at` |
| `goal_todos` | 目标↔事项 | 支持关系（`relation = support | next`），**不是**父子 |
| `goal_milestones` | 目标↔里程碑 | 承载关系，多对多，带 `position` |
| — | **计划** | **不存在**。`PlanSurface` 由 `todos` 的到期日推导：全部／今天／接下来／未排期 |

两处「关系有了但界面看不见」（grep 事实）：

- `src/application/read-models/dashboard.ts` 为每条事项算了 `milestone_status` 与
  `milestone_open_todo_count`（`t.milestone_id ? … : …`），
  但 `client/**` 里 **0 处使用**这两个字段。
- 事项→里程碑的可见线索只有三处：事项行尾的里程碑名（`KanbanView.tsx` 的 `t.milestone_title`）、
  事项编辑器的「里程碑」下拉、筛选弹层的「所属里程碑」。**没有任何地方显示「这个阶段下有几件事在推进」**。

## 3. 界面事实：用户实际能看到什么

| 一级入口 | 装什么 | 关键文案 |
|---|---|---|
| 首页 | 需要回应的判断／提醒／今日安排 | 「今天」「最近变化」 |
| **计划** | **开放事项**按到期日分段 | 「全部计划」「今天／接下来／未排期」 |
| **目标** | **目标**＋每个目标承载的里程碑＋「其他里程碑」轴 | 「目标与里程碑」「里程碑：」「其他里程碑／不属于上面任何目标」 |
| 历史 | 已完成／已取消／最近变化 | 「按时间／按事项」 |

各对象的**可见入口清单**：

- **事项**：首页、计划、历史、目标卡的「当前下一步」 → 入口充足。
- **目标**：目标页 → 单一但明确。
- **里程碑**：目标卡的胶囊、目标页底部时间轴、事项行尾后缀、筛选下拉、事项编辑器下拉
  → **处处可见，但没有任何一个地方解释它是什么，也没有独立入口**。

判断：用户被迫从「它出现在目标卡片里」推断它是目标的子东西，从「它也能挂事项」推断它可能是容器——
而这两条推断都与设计承诺（L98、L102）相反。

## 4. 用户能否直接理解：逐项判定

| 概念 | 界面给了什么 | 用户还得自己补什么 | 判定 |
|---|---|---|---|
| **计划** | 一个页面名，里面是事项的时间划分 | 得知道它**不是**「目标／里程碑的集合」 | ⚠️ 命名误导（中文语感冲突） |
| **事项** | 勾选框、到期日、提醒 | 无 | ✅ 自明 |
| **目标** | 完成标准、当前下一步、目标日期、进度、推进／暂停／达成 | 得先有一个真实目标才能体会到区别 | 🟡 需要一次示例 |
| **里程碑** | 名字＋日期＋状态胶囊 | 得知道它是**结果**不是动作、可以不属于任何目标、不是事项容器 | ❌ 无处可学 |

**总判定：三者中只有「事项」自明；「里程碑」目前完全依赖用户自己猜。**
这与设计文档自己定的 M4 验收条款（L475「用户不看设计文档，也能在几秒内说清事项、里程碑和目标的区别」）尚有距离。

## 5. 真实数据证据（本机，非夹具）

3 个有内容的存储（脚本见 §9）：

| 存储 | 目标 | 里程碑 | 开放事项 |
|---|---|---|---|
| `dsh-yolo/.dsh/yolo/yolo-65c0ede8ba5b_default.db`（本项目工作区） | **0** | 2 | 5 |
| `SkillSEO/.dsh/yolo/yolo-3ef670deee2d_default.db` | 1 | 1 | 0 |
| `dsh-yolo/.dsh/yolo/yolo-decf873e665c_main.db`（旧 scope） | **0** | 1 | 5 |

关键观察（原文照录）：

```text
MS 进行 PRD 设计          [planned] target=2026-08-30 | 目标归属=0 | 挂在它下面的 todo: —
MS 发布 0.5.0 版本        [planned] target=—          | 目标归属=0 | 挂在它下面的 todo:
                                                        更新文档(pending) | npm 发包 0.5.0(pending) | 更新标签(pending)
无里程碑的 todo: 实现通知一键清除和单条叉掉按钮并测试后推送远程 | 重新梳理计划 Tab 中今天/接下来与历史 Tab 的设计

GOAL [candidate] Capability-evidence-anchored skill-selection defense
     criteria=— target=— progress=0 | milestones=[] | todos=[]
MS   [planned]   能力真值实验：30 skill + 120 请求 + 独立验收 | 目标归属=0
```

三条推断（标注为**判断**，依据为上面的数据）：

1. **目标实际上没被使用。** 全局只有 1 个目标，且是 `candidate`、无完成标准、无日期、无关联；
   而正在进行的 0.5.0 发布**没有目标**，只有一条里程碑和 5 条事项。
   → 用户问「目标和计划有什么区别」，是因为他**没有目标这个概念的使用经验**，不是因为文案写得不好。
2. **里程碑被当成「项目分组／父容器」在用。** 「发布 0.5.0 版本」下面挂了 3 条事项
   （更新文档、npm 发包、更新标签），且它**不属于任何目标**——它实际扮演的是「发布这件事的根节点」。
   这与设计承诺「里程碑不是事项容器」（L102）相反。
3. **抽取把「行动」写成了「里程碑」。** 4 条里程碑里 2 条是行动／安排口吻：
   「**进行** PRD 设计」（进行…是动作；按 L61 的正确形态应是「PRD 设计完成」或一条事项）、
   「能力真值实验：30 skill + 120 请求 + 独立验收」（是一个实验**安排**）。
   → 抽取提示词只有一句判据（`src/extract/prompt.ts` L51：
   `milestones: NEW named project phases or checkpoints with target dates`），
   既没有「结果 vs 动作」的判别规则，也没有「不要用里程碑给事项分组」的约束；
   模型于是按「带日期的项目步骤」归类。

## 6. 根因（三类，各自独立可修）

- **A. 命名与层级**：`计划`（视图名，= 事项的时间划分）与 `目标／里程碑`（实体类别）不同层却平级出现；
  里程碑被提为一等公民，却没有自己的入口与解释落点。
- **B. 可见性**：归属关系昨天才修（`8a64b21`）；事项↔里程碑的计数投影算了不用；
  里程碑**没地方**回答「这是什么」。
- **C. 抽取策略**：prompt 缺少「结果 vs 动作」判据和「里程碑 ≠ 分组」约束，导致入库形态本身就模糊——
  后面的界面无论怎么写都救不回来。

## 7. 建议（按风险分档，可直接排期）

### T0 · 纯文案（零风险，随时可做）

1. **计划页副标题划边界**：「计划 ＝ 要做的事（按时间）｜目标 ＝ 要达成的结果」。
2. **目标页里程碑区加一句定义**：「里程碑是阶段的**结果**（如「内部评审完成」），不是要做的动作。」
3. **首次使用/空态给三行对照**（事项／里程碑／目标各一句例），放在目标页空态里，成本最低、收益最高。
4. **修文档漂移**：`docs/design/goal-management.md` §5.2 的「计划 → 目标」表述。

### T1 · 小改动（一次提交内可完成，有测试可覆盖）

5. **把已算好的关系显示出来**：目标卡的里程碑胶囊上补「N 件事在推进」（数据已存在：
   `milestone_open_todo_count`），让「里程碑不是容器、但确实有支撑」这件事可见。
6. **里程碑胶囊可点跳到事项**：点击后按该里程碑筛选计划页（复用「筛选 → 所属里程碑」的既有能力）。
7. **「计划」页签改名待定**（见下方需你决策项）。

### T2 · 需要设计或抽取侧改动

8. **抽取提示词补判据**：新增「结果 vs 动作」判别与反例（「进行 X」→ 事项或「X 完成」里程碑），
   并写明 `todos.milestone_title` 表示「支撑／对应」，不是父子；同步补 RM 判例。
9. **目标进度来源可解释**：`progress_source = milestone_evidence` 已有，
   但界面不说明「这条进度来自哪个里程碑」。
10. **里程碑是否需要独立入口**（低成本形态：目标页内加「所有里程碑」区，现有时间轴已是雏形）。
11. **用真实数据做分类回归**：把 §9 的脚本扩展成「孤儿里程碑比例 / 目标挂接率 / 动作口吻里程碑占比」。
12. **文档补一章「三对象速查」**，并把它作为对话与抽取的统一定义来源。
