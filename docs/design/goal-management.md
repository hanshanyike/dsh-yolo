# 目标管理产品设计

> 状态：已完成产品设计、产品设计评审和研发评审，待产品确认
>
> 本文重新定义计划页中的“事项、里程碑、目标”，并给出目标的识别、推进和页面方案。本文是产品设计，不代表当前代码已经实现这些能力；“当前实现”与“未来方案”分开描述。

## 0. 先说结论

目标现在之所以让人困惑，不是因为缺少一个按钮，而是因为它没有向用户证明自己为什么独立存在。

当前目标更像“一个长期标题 + 一个进度数字”：它可以被抽取、改名、放弃，进度可以在对话中更新，但用户看不到目标由哪些事项推进、下一步是什么、何时再回顾，也无法从目标页面开始一次有结果的推进。因此它看起来像一个不能完成的特殊事项。

本稿的核心决策是：

1. **事项是行动，里程碑是被用户标记的特殊阶段事项，目标是最终结果。** 三者不是同一层级的三种普通标签：目标管理多个事项，里程碑标记其中具有阶段意义的结果。
2. 用户关于“目标由多个事项完成”的理解是正确方向，但需要补充：事项是目标的推进证据和行动载体，不是把完成数量相加后就能自动证明目标达成。目标是否达成仍由用户依据完成标准确认。
3. 用户关于“里程碑是用户标记的特殊事项”的理解是第一阶段应采用的产品心智：里程碑可以由用户标记和调整，但它的特殊性在于“阶段结果是否成立”，不是普通的待执行动作。它可以有支撑事项，也可以代表外部发生的检查点。
4. 目标、里程碑、事项都允许独立存在，但独立存在的意义不同：事项可以直接提醒；里程碑可以单独记录阶段；目标可以先作为待确认的长期结果存在。活跃目标必须有下一步；如果处于等待或阻塞状态，则必须有明确原因和下次重新判断的时间。
5. 目标的推动不是自动拆解、代办或高频催促，而是围绕“当前状态 → 一个下一步 → 下一次回顾”持续管理，并把决定权留给用户。

推荐的长期关系是：

```text
目标（想达成的结果）
  ├── 直接支持事项（下一步行动）
  └── 里程碑事项（用户标记的阶段性结果 / 检查点）
```

目标直接关联多个支持事项；其中一部分事项可以被标记为里程碑事项，或与一个里程碑建立支撑关系。里程碑不是事项的父容器，不要求所有事项都先经过里程碑。这样既能表达“目标由多个事项推进”，也不会把计划做成复杂的任务树。

## 1. 三种对象到底是什么关系

### 1.1 事项：现在或随后要做的一件具体事情

事项回答的是：**“下一件具体要做什么？”**

它应当有可执行的动作、对象或结果，通常可以由一次行动完成。事项是 YOLO 目前最成熟的管理对象，也是提醒的主要对象。

例子：

- 「周五前把演示稿发给研发」；
- 「确认灰度发布的回滚方案」；
- 「周一和供应商确认交付时间」。

事项的完成标准通常是动作发生或交付物出现。它可以有截止时间、优先级、状态和来源；它可以独立存在，也可以作为某个目标或里程碑的支持事项。

事项不是目标的“子任务字段”而已。很多生活安排、一次性承诺和日程没有更大的目标，也仍然值得提醒和追踪。

### 1.2 里程碑：阶段已经达到的、值得单独标记的结果

里程碑回答的是：**“我们到了哪个阶段？什么阶段性结果已经成立？”**

里程碑更接近“检查点”或“阶段边界”，而不是普通的“下一件动作”。在用户心智上，它是事项的一种特殊类型：用户可以把一个阶段结果标记为里程碑，使它在目标推进和历史中更突出。它通常有一个阶段名称、可选目标日期，以及计划中、进行中、已完成、已放弃等状态。

例如：

- 「完成内部评审」；
- 「测试环境验收通过」；
- 「第一批用户开始试用」。

“准备内部评审材料”是事项；“内部评审完成”才是里程碑。前者描述人要做的动作，后者描述一个阶段性事实是否已经成立。

因此，对“里程碑是用户标记的特殊事项”的评估是：

| 这个理解 | 结论 | 补充边界 |
|---|---|---|
| 里程碑由用户标记 | 接纳 | 用户可以创建、命名、开始、完成、放弃或调整它 |
| 里程碑值得显示在计划中 | 接纳 | 它能帮助用户知道所处阶段，尤其适合有日期的检查点 |
| 里程碑就是一条特殊事项 | 接纳 | 它的语义是阶段结果；可以沿用事项的来源、提醒和历史能力，但状态变化要明确表达为阶段结果 |
| 每个里程碑都必须有支撑事项 | 不接纳 | 外部验收、客户决定、发布结果等可以直接成为检查点 |
| 每个事项都必须属于里程碑 | 不接纳 | 一次性安排和直接支持目标的事项不需要多包一层 |

里程碑不是为了给计划增加第三种颜色，而是当“完成某一步”本身具有阶段意义、需要被回顾或会影响后续判断时，才单独记录。

### 1.3 目标：一段时间内希望达成的最终结果

目标回答的是：**“最终想得到什么变化或结果？”**

目标不是一个更大的事项，也不是一条长期提醒。它应该描述用户想达成的结果、范围或状态，例如：

- 「在 9 月完成产品发布」；
- 「让新同事能够独立完成值班交接」；
- 「今年把英语口语提升到能独立参加工作会议」。

目标的价值在于把多个会话中的事项、里程碑、进展和阻塞连接到同一个结果，并在事项列表之外提供一次“方向回顾”。没有关联行动、阶段或回顾需求的长期句子，通常只是愿望或主题，不应直接成为活跃目标。

### 1.4 推荐关系：一对多支持，不是严格的父子任务树

推荐关系如下：

| 关系 | 是否推荐 | 说明 |
|---|---|---|
| 一个目标有多个直接支持事项 | 推荐 | 这是“目标由多个事项推进”的主要表达；事项是行动，不是目标的完成百分比 |
| 一个目标有多个里程碑事项 | 推荐 | 里程碑事项表达阶段边界，可按时间或结果排列 |
| 多个事项支撑一个里程碑 | 可选 | 事项完成有助于判断里程碑，但不自动等于里程碑完成；这是一种关联，不是父子容器 |
| 一个事项同时属于多个目标 | 默认不推荐 | 会让提醒归属和完成后的影响不清楚；如确实跨目标，保留一个主要目标，其他关系以后再扩展 |
| 一个事项直接支持目标，或与目标的里程碑事项关联 | 推荐 | 两条路径都合法；不强迫没有阶段结构的目标建立空里程碑 |
| 一个里程碑事项必须属于目标 | 不推荐 | 外部阶段、独立项目检查点和一次性验收可以独立记录 |
| 一个目标必须先有事项 | 不推荐 | 用户刚表达目标时可能还没有想好第一步，但激活后必须补下一步或回顾 |
| 事项完成自动把目标设为 100% | 不推荐 | 行动完成不等于最终结果成立，且会制造错误的确定性 |

这里的“支持”比“包含”更准确。目标不是任务树的根节点，里程碑也不是事项容器。YOLO 不需要声称自己知道所有工作；它只需要把用户明确交给它持续跟进的关系记录下来。

### 1.5 三者都可独立存在，但活跃条件不同

#### 事项可以独立存在

这是默认情况。用户说「明天把合同发出去」，YOLO 不应为了形式上的层级而追问目标。事项独立存在就已经有明确价值：记录、提醒、完成、推迟、取消并保留来源。

#### 里程碑可以独立存在

例如「下周客户验收」可能是一个需要关注的外部检查点，但用户没有交代一个更大的目标。它可以独立存在并拥有目标日期。以后用户说“这是发布计划的一部分”，再关联到目标，不需要重新创建。

#### 目标可以独立存在，但分为候选和活跃

目标在用户首次表达时可以先作为“待确认目标”或计划草稿存在；这是为了避免把模糊愿望直接变成长期提醒。用户确认要持续跟进后，才进入活跃目标。

活跃目标不要求立刻拥有完整任务树，但必须满足以下条件之一：

- 已有一个当前下一步；
- 正在等待或受阻，有明确原因，并且有一个下次重新判断的时间；
- 用户明确说“先记下来，之后再规划”，此时应处于待补计划或暂停语义，系统不主动催促。

如果既没有下一步，也没有等待/阻塞原因与回顾时间，页面应把它显示为“待补计划”或建议暂停，而不是伪装成正常推进中的目标。

### 1.6 一个完整例子

```text
目标：9 月完成产品发布
  ├─ 直接支持事项：确认升级说明
  ├─ 里程碑事项：内部评审完成（目标日期：9 月 5 日）
  ├─ 支持事项：整理评审材料
  ├─ 支持事项：邀请研发和产品参加评审
  ├─ 里程碑事项：灰度验证通过（目标日期：9 月 15 日）
  └─ 支持事项：收集灰度反馈并处理阻塞
  └─ 下次回顾：9 月 8 日检查评审是否完成、是否进入灰度
```

这里“整理评审材料”完成，只说明一个行动完成；“内部评审完成”需要用户或明确证据确认；整个“9 月完成产品发布”更不能由事项数量自动推导。

## 2. 什么内容可以成为目标

### 2.1 目标的必要条件

一段用户表达适合成为活跃目标，至少应同时具备以下四类信号中的三类，并且没有明显反例：

1. **结果信号**：描述希望达到的状态、能力、交付结果或变化，而不是单个动作。
2. **持续信号**：预计跨越数天、数周或更长时间，或者用户明确要求持续跟进。
3. **多步信号**：合理判断需要多个事项、阶段、决策或反复回顾；不要求用户一次说出全部步骤。
4. **管理意图**：用户表达了“帮我记着、持续跟进、到时提醒、之后检查进展”等授权。
5. **完成线索**：能说出大致什么情况算完成；若暂时说不清，可以先作为待确认目标，而不是直接激活。

“跨时间”本身不够。句子「下个月提醒我交房租」跨越时间，但仍是一个带日期的事项；句子「以后想学摄影」有长期方向，但还只是愿望。

### 2.2 推荐的目标表达公式

目标可以用下面的产品判断式理解：

```text
目标 = 想达成的结果 + 一段持续时间或持续跟进意图 + 可判断的完成线索
```

用户不需要按模板说话，YOLO 只用它来判断边界。目标标题应尽量保留用户的结果表达，不把它改写成项目管理术语。

### 2.3 分类例子

| 用户表达 | 应归类 | 处理理由 |
|---|---|---|
| 「周三前把客户访谈纪要发给产品组」 | 事项 | 一个明确交付动作，有截止时间 |
| 「下个月完成发布准备」 | 候选目标，确认后激活 | 跨周期结果，但完成范围仍需补充 |
| 「我想在 9 月完成产品发布，帮我持续跟进」 | 目标 | 结果、时间和管理意图都明确 |
| 「先完成内部评审，之后再做灰度」 | 两个里程碑或阶段计划 | 重点是阶段边界；支撑动作再拆成事项 |
| 「整理内部评审材料」 | 事项 | 具体行动，不因服务于目标就变成目标 |
| 「测试环境验收通过」 | 里程碑 | 可观察的阶段结果，适合作为检查点 |
| 「今年提升英语口语，能独立进行工作会议」 | 目标 | 长期能力结果，完成标准较清楚 |
| 「以后想学摄影」 | 愿望 / 待确认目标 | 没有持续跟进授权、时间或完成线索 |
| 「每天提醒我练习 20 分钟」 | 重复事项或跟踪规则 | 重点是提醒节奏，不是最终结果 |
| 「把体重降到 65 公斤」 | 目标或健康计划候选 | 有结果，但是否长期跟进和如何提醒应由用户确认；不应擅自给出健康建议 |
| 「把这个项目做好」 | 不创建目标 | 结果不可判断，应该先追问具体成功标准 |
| 「研究一下要不要换工作」 | 事项或决策探索 | 当前是一次调查/判断，不自动升级为长期目标 |

### 2.4 不应该成为目标的内容

以下情况不应静默创建活跃目标：

- 只有“以后、 someday、想要”而没有持续跟进意图的愿望；
- 一次可完成的动作，即使动作很重要；
- 只有主题或领域，例如“健身”“发布”“英语”；
- 只有压力或情绪，例如“我不能再拖延了”；
- 用户在讨论可能性、询问建议或举例，并没有表达自己的计划；
- 目标结果完全不可观察，也没有可供用户确认的完成线索；
- 目标已经存在但只是一次状态更新，应写入 `updates[]`，不能重复新建。

错误创建目标的代价高于暂时漏掉一个模糊愿望：前者会污染计划页并制造用户不理解的提醒，后者还可以在用户下一次明确表达时补记。

### 2.5 不确定时的确认方式

当同一句话既可能是事项也可能是目标时，YOLO 不应连续追问一整套规划问题，只问一个能决定对象类型的问题：

> 这是一次要完成的事情，还是希望我持续帮你跟进的目标？

用户选择目标后，再在同一次轻量确认中询问一个最小缺口：

> 你希望以什么结果算完成？如果现在还没想好，我先记为目标，之后再一起补。

用户明确说“先记着，不用提醒”时，可以记录为待确认/暂停，不应因此生成主动催促。用户明确说“帮我持续跟进”且结果足够清楚时，可以直接激活，但仍需要在页面提示“下一步尚未设置”。

## 3. 目标如何推动：管理而非代办

### 3.1 推动的定义

YOLO 的推动是让目标持续拥有可理解的状态和下一次判断机会，而不是替用户完成事项。YOLO 可以：

- 记住目标和它的来源；
- 把用户说过的事项、阶段和进展放到正确的目标下；
- 暴露没有下一步、临近回顾、长期无变化或存在阻塞的目标；
- 在合适时机问一个问题，并提供记录、调整、暂停或达成的选项；
- 保留用户对进展和状态的决定及来源证据。

YOLO 不应：

- 自动替用户创建一整套未经确认的任务；
- 因为一个事项完成就自动宣布目标达成；
- 在用户没有授权时联系他人、修改文件、执行外部操作；
- 因为目标长期无变化而高频重复催促；
- 用一个看似精确的百分比掩盖“其实不知道发生了什么”。

### 3.2 最小推进闭环

目标的最小可用闭环是：

```text
表达目标
  → 用户确认是否持续跟进
  → 记录完成线索
  → 添加一个下一步，或设置一次回顾
  → 到回顾点只问一个推进问题
  → 用户记录进展 / 新下一步 / 阻塞 / 调整方向
  → YOLO 更新相关事项、里程碑和目标证据
  → 生成下一次回顾，或由用户暂停、达成、放弃
```

建立目标时不要求完成详细项目计划，但不能让“目标已创建”成为流程终点。最小闭环的验收不是进度条发生变化，而是一次回顾能得到一个明确结果：

- 新增或完成了下一步事项；
- 记录了一个里程碑状态变化；
- 调整了目标范围、期限或完成标准；
- 记录了阻塞和需要用户决定的问题；
- 用户选择暂停、达成或放弃。

### 3.3 三种提醒 / 回顾应该区分

| 触发对象 | 用户看到的问题 | 例子 | 处理结果 |
|---|---|---|---|
| 事项提醒 | “具体要做什么？” | 「今天确认回滚方案」 | 完成、推迟、取消、再次提醒、讨论 |
| 里程碑检查 | “阶段结果是否成立？” | 「内部评审原定今天完成，现在是否已完成？」 | 完成、延期、标记受阻、讨论 |
| 目标回顾 | “方向和下一步是否仍然正确？” | 「发布目标距离上次更新已有一周，下一步还是确认升级说明吗？」 | 记录进展、补事项、改计划、暂停、达成、放弃 |

目标不应复用事项提醒的高频扫描逻辑。目标更适合低频、由回顾日期或明显状态变化触发；一次回顾没有结果时，应延后下一次机会或等待用户主动，而不是立即重复。

### 3.4 “推进目标”交互

目标页面的主按钮建议叫“推进目标”或“更新进展”，点击后进入目标专属的轻量讨论。讨论上下文只带入：目标结果、完成线索、当前里程碑、开放事项、最近进展和来源，不把无关的工作会话混进来。

首屏只引导一个问题：

> 这个目标现在进展到哪里了？下一步是什么？

用户可以用自然语言回答，例如：

- 「内部评审已经完成，下一步确认灰度范围」；
- 「还没开始，因为研发资源没确定」；
- 「这个目标先暂停到下个月」；
- 「已经达到完成标准，可以结束了」。

系统随后只提出确定性、可确认的记录建议。用户确认后，才写入事项、里程碑、目标状态或进度事件。YOLO 可以建议，但不能把建议当作用户授权。

### 3.5 目标进度的语义

百分比不是目标的事实源，也不应成为用户必须维护的 KPI。优先显示这些状态：

- 尚未开始；
- 正在推进；
- 等待下一步；
- 受到阻塞；
- 等待外部结果；
- 暂停；
- 已达成；
- 已放弃。

如果保留百分比，来源必须可解释：

- 用户明确说“完成了一半”时，记录为用户陈述的 50%；
- 用户确认某些阶段完成时，可以根据产品明确的阶段规则建议变化，但不应仅按事项数量自动计算；
- 系统不能把缺少信息写成 0%，也不能把所有事项完成写成 100%。

目标达到完成标准时，应由用户确认“达成目标”。`100%` 只能是这一确认的表现之一，而不是触发确认的依据。

### 3.6 状态与关注信号

目标的持久状态保持克制，推荐：

- **待确认**：识别到了可能的目标，但用户尚未授权持续跟进；
- **进行中**：用户仍希望推进；
- **暂停**：目标仍有价值，但近期不主动回顾；
- **已达成**：用户确认完成标准已经满足；
- **已放弃**：用户明确不再追踪。

“没有下一步”“长期未更新”“有阻塞”“回顾已到期”是关注信号，不要一开始扩展成更多互相排斥的持久状态。它们可以由目标页和提醒系统根据当前事项、里程碑与回顾时间计算出来。特别是“回顾”不能替代下一步：只有处于等待/阻塞且说明原因的目标，才可以没有下一步但保留下次重新判断时间。

## 4. 目标页面应该让用户看到什么

### 4.1 页面任务

目标页不是“目标仓库”，用户打开它主要要完成四件事：

1. 立刻知道每个目标最终要达成什么；
2. 知道最近发生了什么，以及现在卡在哪里；
3. 找到一个可以马上推进的下一步；
4. 在没有合适下一步时，决定补计划、调整、暂停、达成还是放弃。

如果页面只能展示目标标题和进度，用户无法完成以上任务，也就无法理解目标的产品价值。

### 4.2 目标列表卡片

目标列表要保持轻量，不应把详情页的全部字段压在一张卡片上。每个活跃目标卡优先展示：

| 信息 | 用户要理解的内容 |
|---|---|
| 目标结果 | 最终想达成什么，不只显示一个短标题 |
| 状态 | 进行中、待补计划、受阻、暂停、已达成或已放弃 |
| 下一步 | 最近一件开放事项、截止时间和所在阶段；没有时显示“还没有下一步” |
| 下次回顾 | 何时再看，以及是事项提醒还是目标回顾 |

完成线索、当前阶段、最近进展、来源和关联事项数量放入目标详情；它们用于解释和回顾，不应让目标列表变成项目管理清单。

百分比最多作为辅助信息，并且必须附带“来自用户在某次对话中的进度陈述”或类似来源。不要在列表顶部展示“平均目标进度”，它对不同目标没有可比性，也会把用户注意力引向虚假的精确度。

### 4.3 卡片上的操作

目标卡只突出一个主要操作，按当前状态选择：

1. 有下一步时显示 **推进目标**：打开目标专属讨论，记录进展、卡点和下一步；
2. 没有下一步时显示 **添加下一步**：创建一个事项并关联到目标；
3. 目标详情和更多操作中提供设置回顾、更新完成线索、暂停、达成和放弃。

“放弃”可以保留，但应是终止类的次级操作，不应成为目标唯一明显动作。改名是字段编辑，不应承担“推进”功能，也不应与放弃并列成为目标的主要价值。

### 4.4 详情区与空状态

点击目标后，详情区按以下顺序组织：

```text
目标结果与状态
  → 完成线索 / 时间范围
  → 当前阶段与阶段日期
  → 当前下一步（可完成、推迟或讨论）
  → 阻塞与等待中的决定
  → 最近进展及其来源
  → 下次回顾
  → 关联事项和里程碑
  → 历史变化
```

目标没有下一步时，页面不应留白或展示孤立的 0% 进度条，而应给出可行动的空状态：

> 这个目标还没有下一步。你可以添加一件要做的事，设置下次回顾，或先暂停目标。

目标没有关联事项但用户明确要持续跟进时，显示“尚未拆出行动”，并提供“添加下一步”；目标只有愿望、尚未确认时，显示“等待确认”，不要生成主动提醒。

### 4.5 目标页与计划页其他区域的关系

- “今天 / 接下来 / 全部”继续以事项为中心，不把目标标题混入待办清单；
- 目标页显示目标和它的推进上下文，事项仍然可以从自己的计划区域进入；
- 里程碑可以在目标详情中显示，也可以在没有目标时进入独立的阶段检查区域；
- 首页只展示因事项提醒、阶段检查或目标回顾而确实需要用户回应的内容，不展示全部目标积压；
- 历史记录分别保留事项动作、里程碑状态和目标进度/状态变化，不把它们合并成一条模糊的“目标更新”。

## 5. 当前实现：哪些已经有，哪些还没有

以下是基于当前代码和架构事实的描述，不是未来方案的假设。

### 5.1 当前数据关系

当前领域类型和 SQLite schema 体现的是：

- `Todo` 有一个可选 `milestone_id`；一个事项最多直接关联一个里程碑；
- `Milestone` 有标题、描述、目标日期和 `planned / active / done / abandoned` 状态；
- `Goal` 有标题、描述、0–100 的整数 `progress`、`active / achieved / abandoned` 状态，以及一个可选 `milestone_id`；
- 当前没有 `goal_id` 直接连接事项，也没有“一个目标有多个里程碑”的关系表；
- 因此当前实际关系更接近“事项 → 里程碑 ← 目标引用”，不是“目标 → 多个事项”的完整结构。

事实源：[`src/domain/types.ts`](../../src/domain/types.ts)、[`src/storage/schema.sql`](../../src/storage/schema.sql)。

### 5.2 当前抽取行为

当前抽取提示把：

- 跨天或跨周的长期愿望放入 `goals`；
- 新的命名项目阶段或有日期的检查点放入 `milestones`；
- 具体承诺和带日期的安排放入 `todos`；
- 已存在目标的进度变化、已存在里程碑的状态变化放入 `updates[]`。

后台写入时先处理里程碑，再让事项和目标通过标题找到里程碑；Goal 自动继续轮次不会触发普通事项抽取，但用户在目标讨论中的真实输入仍可被捕获。这符合“目标、事项、里程碑是不同语义对象”的方向，但目前没有待确认目标层，也没有完整的目标关联推导。

事实源：[`src/extract/prompt.ts`](../../src/extract/prompt.ts)、[`src/application/ingestion/apply-extraction.ts`](../../src/application/ingestion/apply-extraction.ts)、[`docs/architecture/extract.md`](../architecture/extract.md)。

### 5.3 当前页面和操作

当前计划页的“目标”区域实际上是“目标与里程碑”：

- 只展示 `active` 目标，并显示平均进度；
- 目标卡显示进度条；进度在页面上只读；
- 目标可点击改名，并有“放弃”操作；
- 目标只通过标题匹配展示一个关联里程碑；
- 目标卡没有关联事项、下一步、完成线索、阻塞或下次回顾；
- 没有目标专属的“推进目标”入口；
- 没有目标的“暂停”和“达成”按钮；
- 没有归属于目标的事项清单，未归属目标的里程碑还会单独展示在时间轴上。

服务端动作路径其实已有 `set_progress`、目标改名和放弃，但目标 UI 没有把 `set_progress` 做成用户可理解的推进流程。动作仍应继续走统一的 `POST /yolo/actions → applyYoloAction`，不能为目标另造绕过审计的写入路径。

事实源：[`client/panel/KanbanView.tsx`](../../client/panel/KanbanView.tsx)、[`src/application/commands/apply-yolo-action.ts`](../../src/application/commands/apply-yolo-action.ts)、[`docs/architecture/overview.md`](../architecture/overview.md)。

### 5.4 当前实现带来的产品误解

当前实现会让用户产生四个合理但错误的推断：

1. 目标似乎只是比事项更大、但不能完成的一行记录；
2. 进度百分比似乎是系统计算的客观事实，实际上很多时候只是对话中的一次陈述；
3. 里程碑似乎是目标的装饰时间轴，而不是阶段结果；
4. “放弃”似乎是目标唯一有意义的业务动作。

因此短期不应继续在当前卡片上堆加零散按钮；应先按本稿定义目标的关系和最小推进闭环，再决定数据迁移与页面改造。

## 6. 可落地的最小闭环

目标功能不需要第一版就变成 OKR、项目管理器或自动规划器。建议按以下最小范围实现。

### M0：先让用户能确认对象类型

- 统一对话抽取和快速新增的产品文案：事项是要做的事，里程碑是阶段检查点，目标是持续追踪的结果；
- 对“以后想……”“把这个做好”这类低置信表达进入待确认，不直接成为活跃目标；
- 用户明确说“帮我持续跟进”且结果足够清楚时，允许创建活跃目标；
- 已有的目标、里程碑、事项状态更新继续使用原对象，不重复创建。

这一步不要求立刻增加复杂关系，但必须停止把所有长期句子都当成可提醒目标。

### M1：让目标卡回答“现在怎么推进”

第一版目标页面只需保证每个活跃目标显示：

- 目标结果；
- 完成线索（暂时可以复用现有 description 字段，但界面必须明确其语义）；
- 当前里程碑；
- 当前下一步事项；
- 最近进展及来源；
- 下次回顾或“尚未设置”；
- “推进目标”“添加下一步”“设置回顾”“暂停 / 达成 / 放弃”。

如果当前没有结构化字段支撑某个信息，应显示“尚未设置”，不能用标题、进度或事项数量猜测填充。

### M2：补足最小关系和回顾事实

为了真正表达“目标由多个事项推进”，后续需要一个小而明确的 schema/read-model 扩展：

- 目标可以直接关联多个支持事项；这是“目标由多个事项推进”的核心关系；
- 目标可以关联多个里程碑事项，但里程碑事项不是目标下的事项容器；
- 事项可以可选地关联一个里程碑，表示它支撑或对应这个阶段；里程碑事项可以没有目标，普通事项也可以没有目标/里程碑；
- 里程碑与事项之间的关系是阶段标记或支撑关联，不是父子容器；
- 目标需要保存完成线索、可选目标日期或时间范围、下次回顾时间；
- 目标进展事件保存来源、时间和用户说明；
- 关系和状态变化继续通过 application command、单 workspace transaction 和追加事件写入。

数据设计上优先增加清晰的关系与投影，不要把所有逻辑塞进 `goal.progress`。不建议为了兼容旧字段而把一个目标的多个事项压成 JSON，也不建议让 `goal.milestone_id` 继续承担“一对多关系”的假象。旧目标可以通过迁移成为只拥有一个当前里程碑的目标，再逐步补充其他关联。

研发实现可以采用小型关系表，例如：

```text
goal_todos(goal_id, todo_id, is_primary, created_at)
goal_milestones(goal_id, milestone_id, position, created_at)
```

现有 `todos.milestone_id` 可以继续表示“事项支撑或对应哪个阶段”，但不应被解释为事项的父子层级。现有 `goals.milestone_id` 只作为旧数据兼容投影，不能继续承担一个目标只能有一个里程碑的产品限制。

### M3：让目标回顾可持续但不过度打扰

- 用户可以在目标页或目标讨论中完成一次回顾；
- 到回顾时间时，只投递一条目标回顾，而不是每个关联事项各投递一条；
- 回顾必须能落成进展、下一步、阻塞、改计划、暂停、达成或放弃中的一种结果；
- 没有结果时，降低频率或等待用户重新安排，不无限催促；
- 提醒仍进入 YOLO 自有会话，不注入普通工作会话。

### M4：验证产品是否真的有价值

通过真实对话和浏览器检查以下场景：

1. 用户说一个明确的一次性事项，不会被升级成目标；
2. 用户说长期愿望但未授权跟进，进入待确认或不创建活跃目标；
3. 用户确认一个目标后，能从目标页看到下一步并进入目标讨论；
4. 完成一个事项不会错误地把目标标为达成；
5. 用户说明阻塞、暂停或改变方向后，页面状态和历史都能理解；
6. 目标回顾不会打扰普通工作会话，也不会产生重复提醒；
7. 用户不看设计文档，也能在几秒内说清事项、里程碑和目标的区别。

## 7. 反例：看似合理但不应采用的方案

### 反例一：把目标当成“大号事项”

做法：目标只保留标题、截止日期和完成按钮。

问题：用户仍然不知道目标和事项的边界；目标没有承载多事项、阶段或回顾的价值，最终只会变成更难完成的事项。

### 反例二：把里程碑做成带颜色的事项标签

做法：每个里程碑必须对应一条待办，完成待办就自动完成里程碑。

问题：外部验收、客户决定、上线结果等无法由用户亲自执行的阶段事实无法表达；一个动作完成也不必然说明结果成立。

### 反例三：按事项完成数自动计算目标进度

做法：目标有 10 个事项，完成 5 个就显示 50%。

问题：事项重要性不同，且目标结果可能在没有完成所有事项时已经达成，或完成所有事项后仍未达成。这会制造错误的精确感，并诱导用户为百分比服务。

### 反例四：所有“想要”都自动建目标并提醒

做法：只要用户说“想”“计划”“以后”，就写入活跃目标。

问题：愿望、讨论、举例和真正授权的计划没有区别；目标页变成愿望垃圾桶，提醒信任会下降。

### 反例五：目标页自动生成完整任务树

做法：YOLO 根据目标自行拆出十几项任务并设定期限。

问题：这越过了用户的计划权，也会把模型猜测伪装成用户承诺。YOLO 可以根据用户明确说过的内容整理关系，可以提出一项建议，但不能无确认执行自动规划。

### 反例六：只提供“放弃”避免复杂状态

做法：不实现推进、暂停、达成，只保留放弃。

问题：系统只提供终止路径，没有继续路径，用户自然会把目标理解为无用的记录。状态少不等于语义清楚；“暂停”和“达成”与“放弃”必须区分。

### 反例七：把目标回顾变成每日早报中的固定大段

做法：每天在首页重复列出所有活跃目标和百分比。

问题：目标管理变成噪声，且抢占事项提醒的注意力。目标应按回顾需要、阻塞和无下一步等信号进入注意范围。

## 8. 方案边界与验收标准

### 不在第一阶段做

- OKR 的目标—关键结果—评分体系；
- 多层目标树、复杂依赖图和资源排期；
- 根据目标自动生成并自动执行任务；
- 把事项完成率作为目标完成率的唯一公式；
- 目标与外部 Agent 的自动授权、执行和结果验收；
- 为每个目标增加一套独立于事项提醒的高频通知系统。

这些能力可能在未来有价值，但会先把一个尚未说清楚的对象变得更复杂。当前应证明的是目标能否减少重复交代、让用户及时发现没有下一步，并帮助用户做出继续、调整、暂停或结束的决定。

### 产品验收标准

目标方案达到可用前，至少满足：

1. 用户能用一句话说清：事项是要做的事，里程碑是阶段检查点，目标是持续追踪的结果；
2. 一个目标可以看到多个支持事项，且用户能区分事项完成和目标达成；
3. 里程碑既能关联目标，也能在没有目标时独立存在；
4. 目标卡能直接找到当前下一步或明确显示没有下一步；
5. 目标回顾能产出一个具体记录结果，而不是只改变一个百分比；
6. 完成标准、进度说明、来源和时间可追溯；
7. 待确认愿望不会静默变成活跃提醒；
8. 暂停、达成、放弃三种结果在页面和历史中含义不同；
9. 目标提醒不插入普通工作会话，且不会因多个事项重复投递；
10. 方案能在现有 `domain → application → contracts/read-model → client` 分层内演进，所有写入继续经过统一动作和审计，不引入第二份计划事实。

### 最终判断

目标不是为了让计划页多一个栏目，而是为了管理“多个具体行动共同指向的长期结果”。事项负责行动，里程碑负责阶段判断，目标负责结果和回顾。三者关系清楚后，目标页面的主问题就不再是“如何放弃目标”，而是：

> 这个目标现在要达成什么，当前进展到哪里，下一步是什么，什么时候再看一眼？

只要页面和数据不能回答这四个问题，目标功能就还没有真正形成闭环。
