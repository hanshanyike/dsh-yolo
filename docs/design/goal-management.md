# 目标管理产品设计

> 状态：产品方案，未完全实现
>
> 本文解决一个具体问题：计划中的“目标”为什么存在，以及它如何真正帮助用户持续推进事情。本文描述产品语义和演进路线，不代表当前代码已经具备所有能力。

## 1. 先说结论

当前目标的问题不是少了几个操作按钮，而是没有形成完整的管理闭环。

现在的目标更像是从对话中抽出的标题和一个进度数字。它可以改名、放弃，进度主要通过后续对话更新，但没有明确的完成标准、下一步、回顾时间，也没有充分组织相关事项。因此用户很难理解它和普通事项的区别。

目标应该被定义为：**用户希望在一段时间内达成的结果，以及围绕这个结果持续安排下一步的管理容器。**

目标本身不替用户执行工作，也不应该每天重复提醒一个抽象标题。它的价值是把分散在多个会话中的事项和阶段变化连接起来，让 YOLO 能回答：

- 这件事最终想达成什么；
- 现在处于哪个阶段；
- 下一步是什么；
- 什么时候应该再看一眼；
- 如果没有进展，是继续、调整、暂停还是放弃。

## 2. 三种对象的边界

| 对象 | 回答的问题 | 典型时间尺度 | 主要操作 |
|---|---|---|---|
| 事项 | 下一件具体要做什么？ | 今天到几周 | 完成、推迟、取消、再次提醒 |
| 里程碑 | 到哪个阶段算取得阶段性成果？ | 几天到几个月 | 设置日期、开始、完成、放弃 |
| 目标 | 最终希望达成什么结果？ | 几周到几个月或更久 | 推进、回顾、调整、暂停、达成、放弃 |

例子：

- 「周五把演示稿发给研发」是事项；
- 「完成内部评审」是里程碑；
- 「在 9 月完成产品发布」是目标。

事项可以独立存在。目标则只有在能够影响多个事项、阶段或后续回顾时才有价值。目标不是“更大的事项”，而是事项之间的方向和结果。

## 3. 目标的结构

目标的最小可用结构不是“标题 + 百分比”，而是：

```text
目标：想达成的结果
  ├─ 完成标准：什么情况算达成
  ├─ 时间范围：大致何时达成或何时重新评估
  ├─ 里程碑：重要阶段或检查点（可选多个）
  │    └─ 事项：为阶段或目标服务的具体安排
  ├─ 当前下一步：最近要推进的一个动作
  └─ 下次回顾：YOLO 何时询问进展或提醒重新判断
```

目标不一定一开始就有完整计划，但活跃目标至少应该具备“下一步”或“下次回顾”中的一个。没有这两者的目标只能是候选想法，不能长期占据进行中的计划。

### 3.1 进度不能成为唯一主线

百分比很容易制造虚假的精确感。没有相关事项、里程碑或用户陈述时，`0%` 并不表示系统真的知道目标尚未开始。

产品上应优先展示：

- 尚未开始；
- 有下一步；
- 等待用户判断；
- 受到阻塞；
- 最近一次进展；
- 下次回顾时间。

百分比可以保留，但必须来自用户明确陈述，或来自清晰的阶段完成事实。目标详情需要能看到进度的来源和更新时间，而不是只显示一个不可解释的数字。

## 4. 什么内容可以成为目标

### 4.1 自动识别标准

一段话适合成为目标，通常同时满足以下条件：

1. 描述的是希望达成的结果，而不是一次动作；
2. 预计需要跨越数天、数周或更长时间；
3. 需要多个事项、阶段或决策，或者确实需要定期回顾；
4. 用户明确表达了希望持续跟进、记录或提醒；
5. 能够说明大致完成标准，哪怕还不够精确。

如果只满足“我希望以后……”但没有时间范围、结果或持续跟进意图，不应直接创建活跃目标。可以保留为一次对话中的想法，或在未来提供低打扰的“是否建立目标”建议。

### 4.2 分类例子

| 用户表达 | 应归类 | 原因 |
|---|---|---|
| 「周三前把客户访谈纪要发给产品组」 | 事项 | 一个明确动作和截止时间 |
| 「下个月完成发布准备」 | 目标 | 跨周期的结果，通常需要多个步骤 |
| 「先完成内部评审，之后再做灰度」 | 里程碑/阶段计划 | 表达的是阶段边界 |
| 「今年提升英语口语，能够独立进行工作会议」 | 目标 | 长期结果，有明确能力标准 |
| 「以后想学摄影」 | 暂不创建活跃目标 | 愿望明确，但缺少跟进承诺和下一步 |
| 「每天提醒我练习 20 分钟」 | 事项或跟踪规则 | 重点是重复安排或提醒方式，不是抽象目标 |

目标识别不应只依赖“目标”“计划”这些关键词。相反，也不能因为句子听起来有 ambition 就自动升级为目标。错误建立一个会持续提醒用户的目标，比漏记一句愿望更伤害信任。

### 4.3 不确定时的确认

当一句话同时可能是事项或目标时，YOLO 可以只问一个澄清问题：

> 这是一次要完成的事情，还是希望我持续帮你跟进的目标？

明确表达“目标是……”“接下来几个月要……”并且有管理意图时，可以直接建立目标；只有愿望、设想或讨论时，不应静默创建活跃目标。

## 5. 目标如何推动

YOLO 的“推动”是管理推进，不是代替用户执行。最小闭环如下：

```text
建立目标
  → 确认完成标准
  → 补一个下一步或里程碑
  → 设定下次回顾
  → 到时询问进展 / 暴露阻塞
  → 更新事项、里程碑或目标状态
  → 生成下一次回顾
```

目标提醒和事项提醒也应不同：

- 事项提醒用户“该做什么”；
- 里程碑提醒用户“阶段是否完成”；
- 目标回顾提醒用户“方向是否仍然正确、下一步是什么”。

一次目标回顾只需要促成一个明确结果：记录进展、创建下一步、调整期限、标记阻塞、暂停或达成。没有结果的目标不应被无限重复催促。

## 6. 目标页面应让用户看到什么

目标列表不应只显示一条进度条和“放弃”。目标卡至少应回答五个问题：

1. 想达成什么？
2. 什么情况算完成？
3. 最近推进到了哪里？
4. 下一步是什么？
5. 什么时候再回顾？

主要操作建议为：

- **推进目标**：进入一次围绕目标的轻量回顾，记录进展和下一步；
- **添加下一步**：创建事项并关联到目标或当前里程碑；
- **更新进展**：记录用户明确陈述的进度和说明；
- **设置回顾**：安排下次检查时间；
- **暂停目标**：暂时不再作为活跃计划推进；
- **达成目标**：确认完成标准已经满足；
- **更多 → 放弃目标**：目标不再值得继续追踪。

“放弃”应保留，但降为终止类操作。它不应该成为目标唯一明显的动作。

如果一个目标没有下一步、里程碑或回顾时间，页面应明确显示：

> 这个目标还没有推进安排，需要补充下一步，或暂时暂停它。

不要用一个孤立的 `0%` 进度条掩盖这个问题。

## 7. 状态语义

未来的产品语义可以包含：

- 待确认：从对话中识别出来，但还没有得到持续跟进的确认；
- 进行中：用户仍希望推进，并且存在下一步或回顾；
- 暂停：目标仍有价值，但近期不主动推进；
- 已达成：完成标准已满足；
- 已放弃：用户明确不再追踪。

“有风险”“受阻”“长期未更新”更适合作为根据事项、里程碑和回顾时间计算出的关注状态，而不是一开始就扩展成大量互斥的持久状态。

## 8. 当前实现与方案的差距

当前版本已经能从对话中抽取目标，并通过后续对话更新目标进度；目标也能在计划页显示，并保留改名、放弃和历史变化。但当前目标仍然存在以下限制：

- 目标卡缺少完成标准、下一步和下次回顾；
- 目标与多个事项之间没有完整的直接关系；
- 当前关系更接近“事项关联里程碑、目标引用里程碑”，不能完整表达一个目标包含多个阶段和事项；
- 目标进度在页面上只读，用户不能直接从目标卡发起一次推进；
- 目标自动抽取还没有“候选 / 待确认”这一层；
- 暂停、达成确认和无下一步提醒尚未形成完整体验。

因此，在这些能力补齐前，目标页应被理解为长期计划的观察入口，而不是一个已经成熟的目标管理器。当前代码和稳定架构仍以事项、里程碑和目标的既有字段为准，本文不改变它们的现行接口契约。

## 9. 推荐的演进顺序

### 第一阶段：让目标可理解

- 目标卡展示“完成标准、下一步、下次回顾、相关事项/里程碑”；
- 没有推进信息时显示“尚未开始 / 待补计划”，不显示有误导性的空进度；
- 增加目标详情和“推进目标”入口；
- 将“放弃”放入更多操作，并补充明确的“达成”语义。

### 第二阶段：让目标可组织

- 建立目标与多个里程碑、事项的关系；
- 支持从目标直接添加事项和设置回顾；
- 根据用户确认的里程碑或事项变化展示进展证据；
- 增加暂停和恢复，但保持状态数量克制。

### 第三阶段：让目标可持续跟进

- 对明确目标自动生成低打扰的回顾建议，而不是高频提醒；
- 对模糊愿望进入候选确认，不直接进入活跃计划；
- 识别长期没有下一步、阶段逾期或持续阻塞的目标；
- 让用户在一次回顾中完成“记录进展 → 确认下一步 → 设置下次回顾”。

不建议一开始引入 OKR、复杂依赖图、自动规划或自动执行。目标功能首先要证明的是：用户能看懂它、愿意更新它，并且它确实减少了重复交代和遗忘。

## 10. 验收标准

目标功能达到可用状态前，至少应满足：

1. 用户能在几秒内说清目标和普通事项的区别；
2. 每个进行中的目标都能看到下一步或下次回顾；
3. 目标进度变化能看到来源、时间和说明；
4. 达成、暂停和放弃分别表达不同含义；
5. 模糊愿望不会静默变成持续提醒；
6. 目标回顾能产出具体结果，而不是只修改一个百分比；
7. 目标相关提醒不会插入普通工作会话，也不会制造高频打扰。
