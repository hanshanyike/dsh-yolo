# 通知按钮与通知记录交互设计

> 状态：已实现；本文是通知按钮、通知记录与首页职责边界的设计事实源
>
> 适用范围：助手看板顶部通知按钮、通知记录、首页提醒投影、侧栏角标与新通知轻提示
>
> 相关事实源：[助手看板原型](assistant-dashboard-prototype.md) ·
> [客户端架构](../architecture/client.md) · [看板服务端架构](../architecture/ui.md) ·
> [提醒架构](../architecture/reminder.md)

## 1. 背景

改造前，顶部「通知」按钮显示所有 `handled_at IS NULL` 的 notification 行数，提醒和早晚简报共用
“未处理”语义。点击按钮不会进入完整通知列表，只会回到首页并滚动到 dashboard 当前携带的通知卡。

这造成三个问题：

1. 角标统计全部未处理通知，但 dashboard 只返回最新 12 条且包含已处理行，出现“数字存在、内容不可达”；
2. 首页已经负责事项判断、提醒和处理动作，再增加一个有同样动作的通知中心会重复首页职责；
3. 简报主要用于阅读，却长期占用“未处理”数量，让通知按钮看起来像不断增长的任务积压。

本设计不再把通知面板做成第二个首页。通知按钮只回答“最近有什么新到达”，首页继续回答“现在要做什么”。

## 2. 三个表面的职责边界

| 表面 | 用户问题 | 展示对象 | 状态所有权 |
|---|---|---|---|
| 首页 | 现在最需要我回应什么？ | 去重后的开放事项、助手判断、到期与提醒事实 | 事项状态、提醒处理状态 |
| 通知记录 | 最近有什么新到达？ | 每一次提醒和简报投递记录 | 通知已读状态 |
| 历史 | 已经发生了什么变化？ | 完成、推迟、取消等用户可理解的变化 | 审计事件 |

三者不能相加，也不互相复制操作：

- 首页可以完成、推迟、取消、讨论或“知道了”；
- 通知记录只能阅读通知、展开正文和打开关联事项；
- 历史用于回顾变化，不承担提醒处理。

例如当前有 7 件开放事项、24 条今日变化，用户离开期间新到达 2 条提醒和 3 份简报：

```text
首页：7 件需要处理
历史：24 条变化
通知按钮：5 条新通知
```

用户打开通知记录后，按钮数字变为 0；如果事项仍未处理，首页仍然保持 7 件。这样“看过通知”和“处理了
事情”不会混为一谈。

## 3. 核心设计决策

### 3.1 按钮数字表示未读，不表示待办

顶部数字只统计 `seen_at IS NULL` 的 notification，包括提醒和简报。它是“新到达通知数”，不是未完成
事项数，也不是待回应提醒数。

打开通知记录时，以服务端提供的打开基线标记此前通知为已读；打开之后到达的通知继续计数。按钮数字可以
归零，但首页事项不会因此消失。

### 3.2 通知记录只有一个时间流

不增加“待处理 / 简报 / 全部”Tab，不增加提醒置顶区，也不增加独立简报中心。提醒、早报和晚报按到达
时间出现在同一个列表中，用卡片类型和图标区分。

### 3.3 通知记录不复制首页动作

提醒卡不提供完成、推迟、再提醒或“知道了”。绑定事项时只有一个主动作“查看事项”，由它回到首页或事项
详情。用户需要处理时进入首页的统一事项交互，避免相同动作在两个表面产生不同回执和状态。

### 3.4 完整可达，不依赖 dashboard 切片

通知记录通过独立分页端点读取完整历史。dashboard 只携带首页需要的提醒投影，不能再把有限的 12 条通知
切片作为“查看全部”。每一条计入按钮数字的通知必须能在通知记录首屏或“加载更多”后找到。

## 4. 信息架构与打开方式

通知按钮打开一个新的单一前景类型 `notification_log`，复用现有上下文区域：

```text
顶部「通知」按钮
  ↓
通知记录（一个按时间排序的列表）
  ↓ 点击关联提醒
关闭通知记录，回到首页并打开对应事项
```

通知记录不是第四个一级页面。首页、计划、历史仍是主看板的三个一级页面；通知记录属于顶部全局动作打开
的前景上下文，与助手对话、事项详情、事项讨论和来源预览互斥。

### 4.1 响应式呈现

| 可用空间 | 呈现方式 | 返回行为 |
|---|---|---|
| 足够并列 | 主面右侧 340px 上下文区 | 关闭后恢复此前主面与前景 |
| 空间不足 | 进入 focus，通知记录替换主面 | 返回恢复此前页面和滚动位置 |
| 340px 紧凑面板 | 单列时间流，不增加二级导航 | Esc 或返回按钮关闭 |

如果打开通知记录前已有事项详情、来源或对话前景，通知记录暂时替换它；直接关闭通知记录时恢复此前前景，
不清除讨论 episode、草稿、请求状态或详情编辑草稿。

从通知卡点击“查看事项”则是明确导航：关闭通知记录，切到首页并打开目标事项详情；之后返回应回到首页该
事项，而不是重新打开通知记录。

## 5. 通知按钮

### 5.1 视觉状态

| 状态 | 按钮呈现 | 可访问名称 |
|---|---|---|
| 无新通知 | `铃铛 + 通知` | `通知，无新通知` |
| 有新通知 | `铃铛 + 通知 + N` | `通知，N 条新通知` |
| 部分工作区失败 | `N+`，tooltip 说明部分加载 | `通知，至少 N 条新通知，部分工作区不可用` |
| 数字超过 99 | 视觉显示 `99+`，读屏读取精确数 | `通知，136 条新通知` |

按钮只有一套数字和一个概念，不再同时表达“待处理提醒”和“新简报”。按钮选中时使用与一级 Tab 一致的
克制激活态，不使用呼吸、抖动或红色告警动画。

新通知到达可以执行一次不超过 160ms 的数字 crossfade；`prefers-reduced-motion` 下即时更新。轮询没有
变化时界面保持静止。

### 5.2 点击与键盘行为

- 点击关闭状态的按钮：打开通知记录，并以服务端时间建立已读基线；
- 点击已打开状态的按钮：关闭通知记录并恢复此前前景；
- Enter / Space：与点击一致；
- Esc：关闭通知记录并把焦点还给通知按钮；
- 点击提醒轻提示：将该通知标为已读，直接打开关联事项；没有关联事项时打开通知记录并定位该行；
- 点击简报轻提示：将该通知标为已读，打开通知记录并定位该简报；
- 通知记录打开期间新通知到达：数字更新，但不抢焦点、不强制滚动。

按钮使用 `aria-expanded` 和 `aria-controls` 关联通知记录；数字变化通过现有单一 polite live region 播报
一次，不能让每次 badge 轮询重复朗读。

## 6. 通知记录布局

```text
┌─────────────────────────────────────┐
│ ←  通知                        刷新 │
│ 最近到达的提醒和简报                 │
│                                     │
│ 今天                                │
│ ┌ 到期提醒                     10:30 │
│ │ 把演示稿发给研发                    │
│ │ 到期 今天 15:00 · dsh-yolo         │
│ │                         [查看事项] │
│ └────────────────────────────────── │
│ ┌ 早报                         09:00 │
│ │ 今天没有明确到期事项……              │
│ │                    [展开 / 收起]   │
│ └────────────────────────────────── │
│                                     │
│ 昨天                                │
│ ...                                 │
│                                     │
│              [加载更多]             │
└─────────────────────────────────────┘
```

### 6.1 排序与分组

- 全局按 `created_at DESC` 排序，相同时间使用稳定 id 打破平局；
- 按“今天 / 昨天 / 更早”分组；
- 不把未处理提醒置顶，避免重新制造第二个首页；
- 新通知用一个低强调度的“新”标识，打开后的当前列表仍保持原顺序，不因标记已读而跳动；
- 已读历史使用次级文字，不用删除线或灰掉整个卡片。

### 6.2 分页

- 首次加载 20 条，底部使用明确的“加载更多”，不使用自动无限滚动；
- 加载更多失败时保留已加载内容并在按钮位置提供重试；
- 通知记录关闭并重开时恢复本次宿主运行期内的滚动位置；
- “全部”一词只在确实能继续分页读取完整历史时使用，不能指代 dashboard 的有限切片。

MVP 不显示 Tab、筛选按钮或搜索。只有真实通知量证明顺序浏览不足时，才依据使用数据增加搜索或筛选。

## 7. 通知卡

### 7.1 绑定事项的提醒

显示通知标题、到达时间、事项截止时间、工作区和当前事项状态。唯一主动作是：

- **查看事项**：关闭通知记录，切到首页并打开对应事项详情。

卡片不提供完成、推迟、再提醒、讨论或“知道了”。这些动作由首页和事项详情统一提供。通知已读状态与事项
是否完成、提醒是否已处理没有绑定关系。

同一事项的多次提醒在通知记录中按投递记录逐条展示；首页仍按事项去重。这样通知按钮数字与通知记录行数
一致，首页工作量也不会被重复提醒放大。

### 7.2 独立提醒

没有 `todo_id` 的 reminder 显示“独立提醒”标签和正文，不伪造事项详情或完成动作。卡片可提供一个次级
“和助手聊聊”入口，将通知正文作为有限上下文传给整体助手对话；如果该入口在评审中仍被认为过重，MVP
可以只保留阅读正文。

### 7.3 简报

简报只是通知记录中的一种卡片，不是独立产品区域。默认显示标题、时间和两到四行正文；点击卡片或“展开”
查看完整正文。MVP 不提供“知道了”“标为已读”或独立简报操作，已读由打开通知记录的基线统一处理。

### 7.4 失效关联

如果 reminder 的 `todo_id` 已不存在、已合并且无法解析，通知记录保留为历史记录并降级显示：

```text
原事项已不可用 · 这是一条早期提醒记录
```

不显示“查看事项”。正常领域动作和测试清理应主动处理关联提醒，失效关联用于迁移与异常恢复，不应影响
首页待处理事项数。

## 8. 与首页的关系

| 内容 | 首页 | 通知记录 |
|---|---|---|
| 绑定开放事项的提醒 | 折叠进事项，提供完整处理动作 | 保留每次投递，只能查看事项 |
| 独立提醒 | 有需要时作为“需要回应”行 | 保留投递正文 |
| 早晚简报 | 不再堆叠通知卡 | 统一时间流中阅读 |
| 已读通知 | 不影响首页 | 保留历史记录 |
| 已处理提醒 | 从首页提醒投影退出 | 仍保留投递记录和当前事项状态 |
| 今日变化 | 最近变化摘要 | 不作为通知复制 |

通知按钮点击后不再滚动首页。首页现有通知卡堆栈应移除：绑定提醒跟随事项，早晚简报进入通知记录。首页
如需“今天收束一下”，应由首页自己的实时事项与变化投影生成，不直接复用历史简报卡。

## 9. 状态模型

### 9.1 已读与已处理分离

notification 保留现有 `handled_at`，新增 `seen_at`：

| 字段 | 所属职责 | 含义 |
|---|---|---|
| `seen_at` | 通知按钮与通知记录 | 用户已经看到这次通知投递 |
| `handled_at` | 首页提醒投影与领域动作 | 用户明确回应了提醒，或关联事项动作使提醒失效 |

```text
新通知 ──打开通知记录──→ 已读通知
   │                         │
   └──首页事项动作──────────→ 提醒已处理 / 事项状态变化
```

两条路径彼此独立。查看通知不能完成事项，处理事项也可以在用户没有打开通知记录时直接让提醒失效。

### 9.2 已读基线

打开通知记录时，客户端先从服务端获得 `opened_at`，再提交“将 `created_at <= opened_at` 的通知标记为已读”。
这样请求过程中到达的新通知不会被误清零。动作必须幂等，并按工作区失败隔离。

### 9.3 迁移

首次升级时执行一次幂等迁移：

1. 旧 notification 不在升级瞬间制造几十条“新通知”，统一以迁移时刻建立已读基线；
2. 保留原 notification id、创建时间、正文、`handled_at` 和工作区；
3. 绑定终态事项的旧提醒继续按领域规则处理 `handled_at`，但不影响通知历史可见性；
4. 无法解析事项的提醒保留为降级历史，不进入首页提醒投影；
5. 迁移必须跨工作区幂等并通过 SQLite 完整性检查。

## 10. 服务端与共享契约

### 10.1 轻量 badge

`GET /yolo/badge` 建议返回：

```json
{
  "unseen": 5,
  "recentNotifications": [],
  "partial": false,
  "revision": 42
}
```

兼容一个版本保留旧 `unhandled` 字段，但新客户端只使用 `unseen`；旧字段不再作为产品按钮语义。

### 10.2 通知分页端点

新增：

```text
GET /yolo/notifications
  ?cursor=<opaque>
  &limit=20
```

响应包含：

```json
{
  "items": [],
  "unseen": 5,
  "openedAt": 1787997600000,
  "nextCursor": null,
  "partial": false,
  "workspaceErrors": [],
  "revision": 42
}
```

游标包含全局排序需要的时间、稳定 id 和工作区身份，对客户端保持 opaque。相同 raw id 在不同工作区继续
以 `(scope_cwd, id)` 区分。一个工作区读取失败不阻断其他工作区，partial 数字只承诺已加载范围。

### 10.3 已读动作

新增统一动作或专用端点，支持两种幂等输入：

- 标记指定 `(scope_cwd, notification_id)` 已读；
- 标记各工作区 `created_at <= opened_at` 的通知已读。

动作回执返回最新 `unseen` 和 `revision`。完整 dashboard 只携带首页业务所需的提醒投影，不再承担通知
记录列表职责。

提醒的 `handled` 动作和事项领域动作保持现有路径，但只从首页、事项详情或助手对话触发。

## 11. 加载、错误与并发

- 第一次打开通知记录先显示骨架，再请求分页端点；不能用 dashboard 的 12 条切片伪装完整列表；
- 已读动作失败时保留数字并显示轻量重试，不阻止用户阅读已加载内容；
- badge 轮询、分页请求和已读动作响应顺序不确定，只接受不早于当前 `revision` 的数字；
- 通知记录打开期间新通知到达，在列表顶部显示“有 1 条新通知 · 查看”，由用户决定是否回到顶部；
- 部分工作区恢复后刷新列表，按 `(scope_cwd, id)` 去重；
- 页面关闭或重挂载不能重复提交已读动作，也不能把打开之后的新通知误标为已读。

## 12. 可访问性与文案

- 通知记录标题、日期分组和卡片使用真实结构语义；“查看事项”有明确可访问名称；
- split 呈现为非 modal complementary region；focus 呈现为 dialog，并正确限制焦点；
- 打开后焦点落在通知记录标题；关闭后回到通知按钮；
- 加载更多后焦点保留在原按钮，新增内容通过 polite live region 宣告数量；
- “已读通知”“已处理提醒”“已完成事项”使用不同文案，不能互相代替；
- 不使用“消息”指代提醒，统一使用“通知 / 提醒 / 简报”；
- reduced-motion 下取消 crossfade 和滚动动画，不改变内容与焦点结果。

## 13. 验收场景

### 13.1 职责边界

1. 7 件开放事项、24 条变化、5 条新通知：三个表面分别显示 7、24、5，不互相求和；
2. 打开通知记录后按钮 `5→0`，首页仍显示 7 件开放事项；
3. 通知记录中的提醒只有“查看事项”，完成、推迟和“知道了”只在首页或事项详情出现；
4. 首页不再堆叠早报、晚报通知卡，通知记录按时间完整保留；
5. 同一事项两次提醒：首页只出现一个事项，通知记录出现两条投递记录。

### 13.2 完整可达

1. 有 36 条通知：首次加载 20 条，加载更多后可以访问剩余 16 条；
2. 最新 12 条均已读、更早仍有记录：分页后仍可找到，不受 dashboard 切片影响；
3. 一个工作区失败：显示至少数量与 partial 提示，成功工作区通知仍可阅读和跳转；
4. 失效关联显示降级记录，不出现无效“查看事项”；
5. 跨工作区同 id 通知不会误合并或跳到错误事项。

### 13.3 已读与并发

1. 打开基线前的通知被标为已读，打开之后到达的通知继续计数；
2. 点击提醒 popup 直接打开事项，只把目标 notification 标记为已读；
3. 完成事项可以处理关联提醒，但不会删除通知历史；
4. 旧轮询结果不能把已归零的数字加回，也不能覆盖更新的 revision；
5. 关闭重开、响应式切换和组件重挂载不会重复提交已读动作。

### 13.4 交互与恢复

1. 从事项详情打开通知记录，直接关闭后恢复原详情和编辑草稿；
2. 从通知卡“查看事项”进入首页正确事项，工作区、来源和提醒状态一致；
3. 340px、479px、标准宽和 split 宽度下无横向滚动，卡片正文和主动作完整可达；
4. 键盘、读屏、reduced-motion、partial 和网络失败路径符合现有 W1–W16 契约；
5. 通知记录打开时新通知不抢焦点、不强制滚动、不替换当前阅读位置。

## 14. 实施拆分

1. **状态与 API**：新增 `seen_at`、未读 badge、通知分页端点、revision、旧数据迁移和跨工作区测试；
2. **通知记录**：实现新前景类型、单一时间流、分页、定位、已读基线、响应式和可访问性；
3. **首页收敛**：移除旧通知卡堆栈，保留事项提醒聚合与统一事项动作；
4. **入口闭环**：调整顶部按钮与 reminder/brief popup 跳转，更新使用文档、架构文档和 W1–W16。

每一步都必须保证旧客户端或旧 payload 有明确兼容边界；不能先移除首页通知卡，再让旧通知继续只存在于
不可达的数据库行中。

## 15. 推荐结论

通知按钮不应再代表“还有多少事情没处理”，这属于首页；它应采用用户熟悉的通知语义：数字表示自上次查看
以来的新通知，点击后进入一个完整的时间记录流。通知记录不提供事项动作，只负责阅读、追溯和跳转。

这一边界既解决当前“36 条但只能看到 3 张卡”的缺陷，也避免新增一个与首页竞争的任务中心。
