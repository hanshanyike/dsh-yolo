# 问题定位：主动提醒「触发了但用户看不见」

> 状态：已定位，待修复 · 定位时间：2026-08-22 · 由真实使用反馈驱动

## 一、现象

用户在会话中交代「5 分钟后提醒我起来活动一下」，等到过期之后，**会话里没有出现任何提醒**。

结论：**调度器完全按设计工作了**——到期后 67 秒内的第一个 tick（间隔 5 分钟）触发，
消息成功投递进「最近活跃的 agent」。断掉的是**最后一公里：投递 ≠ 看见**。

## 三、根因（实证，非猜测）

注入目标是 `latestAgent`——`agent/session-start` 事件最后注册的那个 agent
（`src/reminder/index.ts:34,40-42`）。这是一个**用户不可见、不可控的全局选择**，
且与「用户此刻正在看的会话」没有任何同步机制。实测出两种失败模式：

### 模式一：注入进「空壳会话」，消息滞留内存永不落盘（用户上午的原始案例）

用户在会话里交代待办后，切换到（或新开了）另一个会话等待。新会话触发
`agent/session-start` → `latestAgent` 切到新会话的 agent。但该会话**从未跑过一轮对话**
（没有消息落盘、没有会话文件）——`followup()` 注入的消息排进了这个空壳 agent 的队列，
**既不触发 turn、也不落盘、也不可见**。证据：08:55:51 投递成功（戳已打、队列未用），
但全部会话文件无一在 08:55 有写入。

### 模式二：注入进「过时会话」，提醒与回复都进了没人看的会话（受控复现实锤）

`latestAgent` 停留在上一个 session-start 的会话（实验中为上一个测试遗留的 `s-1b30882a`），
而用户/实验者实际活跃并盯着的会话是另一个（`d96e2e86`）。注入后：
- 提醒消息正常落盘到 `s-1b30882a`（user/message 09:20:51.388）；
- **AI 还在没有任何人查看的会话里生成了一轮回复**（assistant/message 09:20:53.311）——
  不可见，且白白消耗一次 LLM 调用；
- 实验者盯着的 `d96e2e86` 到 09:27:30 零新消息。

### 次要问题

- **投递文本混杂 agent 指令**：提醒消息里写给模型的路由指令（「请用 yolo_action 工具…」）
  以用户消息形式落盘，将来真被用户看到时观感混乱。
- **提醒间隔/提前量配置未接线**：`startReminderScheduler` 支持 `intervalMs`/`aheadMs`
  参数但 `src/reminder/index.ts` 从未传入——间隔写死 300 秒、提前量写死 60 分钟。
  另注意 60 分钟提前量意味着「创建后下一个 tick 就提醒」可能**早于到期时间**——
  「5 分钟后提醒我」实际可能在第 1 分钟就被提醒，语义需在修复时一并澄清。
- **turn 失败无留痕**：注入后 turn 是否执行、AI 是否回复，YOLO 侧完全无感知。

## 四、根因归纳

设计上把「提醒已送达」与「用户已看见」耦合在一个隐式条件上：**用户恰好停留在
latestAgent 会话的界面上**。该条件既不保证成立，也没有任何兜底通道（无未读标记、
无看板通知、无投递留痕），一旦不成立，提醒要么滞留内存（模式一）、要么进幽灵会话
（模式二）——用户无从核实它是否发生过。

## 五、修复方案

| # | 改动 | 解决什么 | 优先级 |
|---|---|---|---|
| 1 | **投递留痕**：提醒触发时写 `reminder_fired` 事件（带 session_id 与目标会话） | 用户至少能在时间线核实「几点提醒过什么」；诊断有据 | P0 |
| 2 | **看板兜底**：侧边栏 YOLO 按钮角标区分「逾期/今日到期」与「已投递未响应」，后者高亮 | 用户不在目标会话时，仍有可见入口 | P0 |
| 3 | **文档明示语义**：使用文档写清「提醒会出现在你交代那件事的会话里」 | 管理预期 | P0 |
| 4 | **投递文本拆分**：用户可见部分（⏰ 提醒正文）与 agent 指令分离（指令放 source 元数据或独立的系统段） | 观感与可维护性 | P1 |
| 5 | **turn 失败留痕**：followup 后无法直接观测 turn 结果（异步），改为在会话侧记录或对 `reminder_fired` 补一个「已响应/未响应」判定（例如 24h 内无该待办状态变化则标记未响应） | 让注入后的静默失败可发现 | P1 |
| 6 | **提醒间隔/提前量配置接线**：`startReminderScheduler` 支持 `intervalMs`/`aheadMs` 参数，但 `src/reminder/index.ts` 从未传入（也不读 settings）——间隔写死 300 秒、提前量写死 60 分钟。若设置界面暴露了这两项，当前是死配置 | 配置真实生效 | P1 |
| 7 | **投递目标改为「创建该待办的会话」**：待办落库时记录来源会话 id（提取/`memory_write` 路径都有会话上下文），投递时优先该会话的 agent，其次 latestAgent，都没有则排队。用户对「提醒出现在我交代事情的那个会话」有天然预期，模式一/二同时缓解 | 直击两种失败模式的目标错位 | P1 |
| 8 | **目标选择显式化**（与路线图「提醒型对话」合流）：提醒最终应进入 YOLO 自己的一方会话，而不是借用某个用户会话——这是治本方案，单独立项 | 治本 | P2 |

## 六、验收标准

1. 在会话甲交代一条 5 分钟后到期的待办，**切换到会话乙**等待；
2. 到期后 ≤5 分钟：**会话甲**收到提醒（投递目标是待办的来源会话，不再依赖 latestAgent）；
3. 同时：看板时间线出现 `reminder_fired` 事件（含目标会话 id）；侧边栏角标出现「已投递未响应」提示；
4. 回到会话甲回复「已完成」→ 角标消失，待办关闭；
5. 极端情况（来源会话与 latestAgent 都不可用）→ 提醒排队，下次任一会话启动时补发；
6. 单测覆盖：tick 触发即写 `reminder_fired` 事件；投递目标解析顺序（来源会话 → latestAgent → 排队）；角标数据来自 dashboard API 的新字段。
