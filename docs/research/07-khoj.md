## 定位与主张

Khoj 是「个人 AI 第二大脑」，强调**从一个入口同时触达你的文档和整个互联网**。它不只做检索：能建自定义 Agent、排 schedule automations（定时自动化）、做深度研究、发 smart notifications（智能通知）。多端覆盖：浏览器、Obsidian、Emacs、桌面、手机、WhatsApp 等。它把「记住你的资料 + 主动替你办事 + 主动通知你」做成一个完整产品形态。

## 核心记忆机制 / 架构

- **RAG / 语义检索为核心**：从个人文档（PDF、Markdown、Notion、Word、Org-mode 等）与网页中检索知识作为上下文。
- **记忆 / 上下文工程**：对用户资料建索引 + 语义搜索，把相关片段注入对话；支持把多个 LLM（本地或云端）接入。
- **Agent + 自动化**：自定义 agents（带白名单工具 / research mode）；schedule automations（定时任务）；smart notifications（到点/按条件通知）。
- **CLI 与自托管**：数据可放自己的服务器；云端/自托管双路径。

## 与「个人 AI 助手（记忆+提醒+看板）」的契合度

**高、但模式不同**。Khoj 已经覆盖「长期知识检索 + 多端访问 + agent + 自动化 + 通知」的完整助手形态，是「产品形态与场景覆盖」的标杆。但它的核心心智是**知识检索型第二大脑 / AI 搜索 / 自动化工作台**，不是「跨会话长期记忆 + 提醒 + 看板管理」这一专职产品；其「主动通知」更像自动化的一环，而非"你说了某件事、它帮你把这件事沿着轨道推进"的记忆编排。

## 明显的不足 / 局限

1. **功能复杂、工程体量大**：作为记忆层参考需要大裁剪；作为产品则与其自研看板不同源。
2. **依赖外部文档索引、语义搜索、LLM 服务**：本地优先与隐私边界不如 Basic Memory 这类 MCP 记忆层清晰。
3. **AGPL-3.0** 对商业闭源集成不友好。
4. **提醒/待办/看板不是核心产品心智**：任务生命周期、完成/推迟/撤销状态机、低打扰通知这套「管理」体验，不是它的重点。
5. 更偏「你主动来问它 / 它按 schedule 跑自动化」，与 dsh-yolo「每次会话结束自发沉淀、合适时机提醒」的持续性、侵入性更轻的定位不同。

## 对 dsh-yolo 的借鉴点

1. **产品形态标杆**：多端触点（浏览器/桌面/消息 App/移动）、自定义 Agent、自动化、通知——可作为 dsh-yolo 场景覆盖的参照清单。
2. **Smart notifications 的「主动通知」方向**：启示 dsh-yolo 把「提醒」做成有节制的智能通知面，而不是打扰式弹窗。
3. **把个人文档纳为记忆源**：Khoj 从本地文档检索的 RAG，可启示 dsh-yolo 未来的档案/知识接入（呼应 dsh-mnemon 的「档案」层）。
4. **多 LLM 可插拔**：代码与「模型运行时」解耦，值得 dsh-yolo 在抽取/召回模型选择上借鉴。

## 一句话结论

**「完整个人 AI 第二大脑」的产品形态标杆**，覆盖面广、仍在维护，作为「产品/场景」方向与「多端 + 自动化 + 通知」的参考最有价值；但它的专长是知识检索而非「跨会话记忆 + 提醒 + 看板管理」，且 AGPL 与云依赖使其更适合当对标而非当依赖。
