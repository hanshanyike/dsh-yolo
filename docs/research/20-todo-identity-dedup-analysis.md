# 事项重复、状态流转与多会话关联分析

> 状态：分析结论已评审；第十三节的最小方向已批准进入 v0.4.0-rc5 实现。
>
> 本文仍以问题分析和目标模型为主，不把路线中的后续能力写成当前实现。实施状态与剩余工作见
> [事项身份与去重路线](../roadmap-todo-identity.md)。

## 一、结论摘要

当前重复问题不能只靠“把标题再标准化一点”解决。YOLO 实际上混在一起处理了四件不同的事：

1. **输入幂等**：同一条用户输入、同一次工具调用或同一轮抽取不能重复落库；
2. **事项身份**：不同表达究竟是在说同一件事、同一件事的新变化，还是一个新的发生实例；
3. **业务状态**：事项处于待处理、进行中、完成或取消；
4. **记录状态**：一条数据库记录是否仍是规范事项，还是已被合并、替代或判定为误提取。

当前实现对第 1 项有部分保护，对第 3 项已有领域动作，但第 2 项主要依赖标题，第 4 项则借用了
`cancelled`。这会产生两个方向相反的错误：

- **漏合并**：同一事项换一种说法、出现在另一个会话或由助手再次写入时，生成多条开放事项；
- **误合并**：周期任务、不同项目中同名事项或同一标题的不同发生实例，被当成同一事项更新。

建议采用以下总体模型：

```text
用户消息 / 助手操作 / 看板操作
          │
          ▼
不可变来源记录（一次输入只登记一次）
          │
          ▼
身份裁决：LINK / UPDATE / REOPEN / NEW_OCCURRENCE / CREATE / ASK / NOOP
          │
          ▼
规范事项（一个当前状态） ── 关联多个会话、轮次、助手操作和历史证据
```

核心原则是：**多次提及不等于多个事项；多个事项也不能仅因标题相似就自动合并。**

## 二、本文讨论的“重复”是什么

重复至少分为五类，必须分别处理。

| 类型 | 示例 | 正确结果 |
|---|---|---|
| 请求重放 | 浏览器或工具重试了同一个写请求 | 原结果重放，不再次写入 |
| 同轮双写 | 主 Agent 先调用 `memory_write`，后台抽取又得到同一事项 | 一个事项，一组来源证据 |
| 跨会话复述 | 会话 A：“周五发演示稿”；会话 B：“别忘了把材料发给研发” | 关联到同一事项，必要时更新字段 |
| 语义近重复 | “把演示稿发给研发”与“向研发发送演示材料” | 高置信时关联，歧义时确认 |
| 假重复 | 本周与下周各有一次“写周报” | 两个发生实例，不能合并 |

此外还要区分“父事项与步骤”。“准备 rc4 发布”和“补测试”可能是父事项与执行步骤，不一定是
重复，也不一定应成为两个平级提醒。该问题已在
[承诺提取重构讨论稿](19-commitment-extraction-redesign.md)中分析，本文只把它作为身份裁决的一种关系。

## 三、改造前基线（v0.4.0-rc4）

本节与后续问题场景记录的是提出改造时的基线，用来解释为什么需要本轮工作；不作为 rc5 之后的架构
事实源。已验证实现以[存储架构](../architecture/storage.md)和[提取架构](../architecture/extract.md)为准。

### 3.1 已有防重措施

当前主链路已经具备以下保护：

- `agent/pre-step` 只捕获 `source.kind=user` 的直接用户输入；Goal 自动 round 不再触发抽取；
- 同一 session 内后台抽取按队列串行，并用 `${sessionId}:${turn}` 防止同 turn 重复调度；
- `extraction_log` 以 `(session_id, turn_seq, strategy)` 唯一记录抽取审计；
- `upsertTodo` 使用 `todo:${normalize(title)}` 作为 `dedup_key`；同 scope、同规范化标题且命中开放行时更新原行；
- 同一轮中主 Agent 的 `memory_write` 会创建 `source=tool` 的 provisional 行，后台抽取可按同 session、
  时间窗口和标题包含关系复用该行；
- 完成、开始、取消和相同截止时间的重复状态动作大多是领域 no-op；
- HTTP 看板动作支持 `client_action_id` 持久幂等；
- 已发现的开放重复项可以通过显式 `consolidate` 合并，并写 `todo_consolidated` 审计。

当前健康检查中的 `duplicateTodos` 只报告规范化标题完全相同的开放项；语义近重复、终态与开放项分叉、
跨工作区重复都不会进入该列表。

这些措施有效，但覆盖的是“同请求、同轮、同标题”这一层，尚未形成完整的事项身份模型。

### 3.2 当前事项来源只有一个主会话

`todos` 当前保存：

```text
session_id       首次来源会话
source_excerpt   首次直接用户原话摘录
source_turn      首次来源轮次
source           llm / tool / manual
```

后续状态动作可以在 `events.session_id` 中留下另一个会话，但这只是动作审计，不代表“该会话讨论过这个事项”。
当前没有 `todo ↔ session` 多对多关系，也没有保存以下信息：

- 后续会话对事项的再次提及；
- 某个新说法为何被判定为同一事项；
- 助手在哪个会话、基于哪条用户消息执行了写入或状态动作；
- 多个会话中的证据哪条是创建、更新、确认、完成声明或普通讨论。

因此当前来源模型更接近“第一次在哪里创建”，还不是“这个事项跨哪些会话持续演进”。

## 四、最可能造成重复的情况

### 4.1 标题相同，但 `dedup_key` 没有唯一约束

`idx_todos_dedup` 是普通索引，不是唯一索引。`upsertTodo` 查询同 key 时也没有明确要求优先选择开放项。
当同一 key 下同时存在终态行和开放行时，SQLite 返回哪一行并没有业务保证：如果先取到终态行，代码会
新建一条事项，即使另一个开放副本已经存在。

直接给规范化标题加唯一约束也不安全，因为“写周报”可以同时存在本周、下周两个发生实例。这里缺少的
不是唯一索引本身，而是**事项身份键 + 发生实例键**。

### 4.2 同一事项换了表达方式

当前 `normalizeTitle` 主要处理大小写、标点和空白；宽松匹配只处理包含关系。以下表达不会稳定命中：

```text
把演示稿发给研发
向研发发送演示材料
把最终 deck 给开发团队
```

LLM 虽然会看到已知事项摘要，但最终写入仍由标题 key 决定。模型只要输出一个不包含原题的改写，就会创建
新行。

### 4.3 已知事项没有进入抽取上下文

已知摘要只取有限数量的事项。事项较多时，正在讨论的旧事项可能不在摘要中；抽取模型便无法稳定输出
`updates[]`，更可能将其作为新 todo 返回。

仅增加摘要条数不是根治：真正需要的是按本轮文本召回相关候选，并把候选的稳定 id、状态、截止时间和
来源证据提供给身份裁决，而不是把固定前 N 条当作完整世界。

### 4.4 多个工作会话并发完成

抽取队列按 session 串行，不按 workspace 串行。两个会话可能同时读取同一份旧 known context：

```text
会话 A 读取：没有事项 X
会话 B 读取：没有事项 X
会话 A 输出：创建 X
会话 B 输出：创建 X 的另一种说法
```

SQLite 最终会串行写入，但语义判断已经基于两个旧快照完成。标题完全相同可能被 upsert 吸收，语义改写则
仍会生成两条。

### 4.5 同一轮 `memory_write` 与后台抽取没有对齐

当前 provisional 升级只覆盖部分情况：

- tool 行必须带同一 `session_id`；
- 创建时间需落在窗口内；
- 标题需要相同，或至少长度满足阈值且互为包含关系；
- 行仍为开放状态；
- scope 必须一致。

以下情况会漏掉：

- Agent 写“发送演示材料”，抽取模型写“把演示稿发给研发”；
- 长轮次、抽取节流或系统繁忙导致时间窗口错开；
- Agent 在工具调用前后切换了工作区归属；
- 工具调用被宿主重试，但工具本身没有稳定幂等键；
- Agent 使用的不是 `memory_write` 入口。

时间窗口只能证明“可能是同一轮”，不能证明“是同一事项”。

### 4.6 YOLO 助手对话与普通工作会话写入纪律不同

YOLO resident/anchored 会话被抽取器跳过，这是正确的防循环措施。但用户在“和助手聊聊”中要求新增事项时，
只能由助手调用工具直接写入：

- 写入来源显示为“助手操作”；
- 不会经过普通工作会话的后台抽取对齐；
- 当前工具调用没有强制先按 id 查询；
- `memory_write` 不携带 `client_action_id`，工具重试可能再次执行；
- 通过标题执行 `yolo_action` 时，歧义候选不会返回给助手，而是选择状态更活跃、更新时间更近的一条。

因此“助手操作”必须被当成一等写入来源，而不是普通抽取的例外分支。

### 4.7 终态后的再次提及无法区分“纠正”与“新一轮”

同标题终态事项再次出现时，可能有三种含义：

1. “刚才不算完成”——应 `REOPEN` 原事项；
2. “下周还要再写一次周报”——应创建新 occurrence；
3. “报告已经发出去了”——只是再次确认已完成，应 `NOOP` 并关联新证据。

当前 upsert 看到终态行时倾向创建新行；模型更新定位又只搜索开放事项，无法稳定表达上述差异。

### 4.8 同一轮先新增、后纠正

用户可能在一个 turn 中连续 steering：

```text
周五把报告发给研发。
不对，改成下周一。
```

如果两句话被模型拆为新 todo 与另一个新 todo，就会重复；如果只保留前一句，又会得到错误截止时间。
正确做法是给同一轮的候选建立顺序，后来的明确纠正覆盖前面的字段，但保留两条来源证据。

### 4.9 跨工作区是同一现实事项

用户可能在“产品仓库”会话里承诺发布，在“文档仓库”会话里继续讨论同一次发布。当前每个 canonical cwd
拥有独立数据库，因此两条记录在存储层不会相遇，而聚合看板只是在读取时把它们放在一起。

跨工作区自动合并风险很高：它会改变动作路由、权限边界和资料归属。合理默认应是：

- 同工作区可进行高置信自动关联；
- 跨工作区只生成候选，必须由用户确认哪个工作区拥有规范事项；
- 另一个工作区的会话作为来源关联，不复制一条可提醒事项。

### 4.10 重试与崩溃窗口

当前 `scheduledTurns` 是内存集合，抽取结果先写领域数据，最后写 `extraction_log`。如果进程在两者之间退出，
宿主重放 turn 时不能依赖 extraction log 预先阻止副作用。精确同标题通常会被 upsert 吸收，但语义改写、
事件和状态动作仍可能重复。

## 五、重复会怎样破坏状态流转

### 5.1 两条开放副本

两条都进入首页、提醒调度和注意力判断，可能分别触发提醒。用户完成其中一条，另一条仍开放，看起来像
“系统没有记住完成”。

### 5.2 一条完成、一条开放

这是最难修复、也最常见的重复形态。当前 `consolidate` 要求两条都开放，因此发现时往往已经不能合并。
用户只能再完成或取消另一条，历史中留下两个看似独立的结果。

### 5.3 用 `cancelled` 表示“已并入”

当前 consolidate 将来源行置为 `cancelled`。业务上“用户取消了事项”和“该记录是重复副本”是不同事实：

- 取消意味着用户不再打算做；
- 合并意味着事情仍然存在，只是由另一个 id 代表。

两者共用状态后会带来三个问题：

- 历史无法准确解释为什么消失；
- 来源副本仍可被普通 `reopen`，再次制造重复；
- 质量学习可能把重复记录误当作用户放弃的事项。

### 5.4 标题动作可能命中错误副本

`findTodoByTitle` 会在多个宽松匹配中选择状态更活跃、更新时间更近的一条，而不会报告歧义。用户说
“把报告标记完成”时，系统可能操作了最近生成的副本，而真正带截止时间和提醒的旧事项仍开放。

**因此状态动作必须优先使用稳定 id；标题只能作为候选检索，多个候选时必须返回歧义。**

## 六、建议的概念模型

### 6.1 规范事项与来源记录分离

`todos` 继续保存“现在是什么状态”，另增加不可变的多来源记录：

```text
todo
  id
  owner_scope_key
  title / detail / due_at / priority
  business_status       pending | in_progress | done | cancelled
  record_status         canonical | merged | rejected
  merged_into_id
  occurrence_key
  created_at / updated_at

todo_evidence
  id
  todo_id
  source_scope_key
  session_id
  turn_seq / message_id
  source_kind           human | assistant_action | panel_action | extraction
  relation              origin | mention | update | correction | completion_claim | discussion
  excerpt
  occurred_at
  source_fingerprint    UNIQUE
```

这里的关键是：

- 一个事项可以有任意数量的来源会话；
- 第一条 `origin` 仍可作为默认来源，但界面可以展开“关联会话”；
- 后续复述只新增 evidence，不创建 todo；
- 业务状态与记录是否被合并彻底分开；
- 历史事件继续不可变，合并后通过 `merged_into_id` 解析到规范事项，不篡改旧事件。

字段名只是讨论建议，最终 schema 应在实现设计阶段确定。

### 6.2 输入登记与身份裁决分离

在写 todo 前登记一次输入事实：

```text
todo_ingest
  source_fingerprint    UNIQUE
  session_id / turn_seq / tool_call_id
  raw candidate
  resolution            create | link | update | reopen | new_occurrence | ask | noop
  resolved_todo_id
  resolver_version
  confidence / reasons
```

`source_fingerprint` 解决的是“同一输入只处理一次”，不能替代语义身份判断。建议优先使用宿主提供的稳定
`message_id`、turn 和 tool call id；没有稳定 id 时才使用 scope、session、turn、候选序号和规范化载荷组成指纹。

### 6.3 身份关系必须显式分类

抽取器不再只输出 `todos[]` 与 `updates[]`，而应先输出关系：

| 裁决 | 含义 | 写入行为 |
|---|---|---|
| `LINK` | 同一事项的再次提及，没有字段变化 | 只增加来源关联 |
| `UPDATE` | 同一事项的截止、标题、优先级或状态发生变化 | 按 id 走领域动作并增加证据 |
| `REOPEN` | 用户纠正终态，原事项仍是同一 occurrence | 重新打开原 id |
| `NEW_OCCURRENCE` | 同一类周期任务的新一次发生 | 新建 todo，关联前一次 occurrence |
| `CREATE` | 新的独立承诺 | 新建 todo |
| `ATTACH_STEP` | 已有事项下的执行步骤 | 保存为步骤/计划，不创建平级提醒事项 |
| `ASK` | 无法安全判断 | 进入待确认，不触发提醒 |
| `NOOP` | 重复确认、闲聊或无管理价值 | 不改状态，可选择只记审计 |

## 七、如何判断“同一事项”

不建议给语义相似度设一个阈值后直接自动合并。身份判断至少需要以下信号：

1. **显式引用**：事项 id、来源会话跳转、提醒卡 id、用户说“这件事”；
2. **完成条件**：是否交付同一结果，而不只是主题相近；
3. **发生实例**：本周与下周、第一次与复查是否是独立 occurrence；
4. **时间兼容性**：新的日期是改期，还是另一项独立安排；
5. **上下文范围**：项目、工作区、客户、收件人、文件或目标是否一致；
6. **状态兼容性**：完成后的提及是确认、纠正还是再次发生；
7. **用户授权**：assistant 建议的步骤是否被用户采纳并要求分别跟踪；
8. **来源连续性**：当前会话是否由事项讨论入口打开，或明确承接另一会话。

建议的裁决顺序：

```text
稳定 id / source fingerprint 命中
  → 确定性 LINK 或幂等重放

否则召回候选（开放项 + 相关终态 + occurrence）
  → 结构化规则排除明显不同项
  → LLM 只在候选之间分类关系并给出依据
  → 高置信 LINK/UPDATE；有风险则 ASK
```

LLM 可以判断语义关系，但不能直接决定删除或合并数据库行。Host 负责幂等、作用域、状态合法性、候选
唯一性和事务。

## 八、分层措施

### 8.1 第一层：立即降低重复率

- `upsertTodo` 明确只在开放行中选择 dedup 候选，并保证选择顺序确定；
- 已知摘要改为按本轮输入召回相关事项，携带稳定 id，不再只依赖固定前 N 条；
- 抽取结果必须区分 `CREATE` 与 `UPDATE/LINK`；
- `memory_write` 和助手动作写入稳定 operation id，工具重试重放原结果；
- 同一 workspace 的“候选解析 + 写入”进入短事务或串行提交区，避免并发会话基于旧快照同时创建；
- 标题动作发现多个候选时返回候选清单，不再静默选择最近一条。

### 8.2 第二层：建立多会话证据

- 新增不可变 `todo_evidence`；
- 现有 `todos.session_id/source_excerpt/source_turn` 迁移为首条 origin evidence，同时保留兼容投影；
- 每次 LINK、UPDATE、状态声明、助手操作都增加一条证据；
- 看板来源从“一个来源”改为“主来源 + N 个关联会话”；
- assistant tool 操作同时记录触发它的用户消息与工具调用，而不是只显示“助手操作”。

### 8.3 第三层：修复合并语义

- 增加独立 `record_status=merged` 与 `merged_into_id`；
- consolidate 允许处理一开一终态等已分叉重复，但必须给出状态冲突解决结果；
- 合并不删除历史事件，所有旧 id 可解析到规范 id；
- 来源、提醒、未处理通知和标题别名合并到规范项；
- 普通 `reopen` 不能重新打开 merged 副本，只能执行“撤销合并”；
- 合并动作可撤销，且必须保留 before/after 证据。

### 8.4 第四层：控制自动化权限

- direct-human 明确承诺可自动 CREATE；
- assistant 规划默认只能形成 proposal 或 step；
- YOLO 助手在用户明确说“记录/提醒/改期/完成”时可以按稳定 id 执行动作；
- 仅凭 assistant 自己的推理不能创建顶层事项；
- 跨工作区 LINK、终态冲突、多个高相似候选和批量 consolidate 一律 ASK。

### 8.5 第五层：可观测与质量反馈

每次裁决至少记录：

- 输入来源与 fingerprint；
- 候选事项 id；
- 裁决类型、规则/模型版本与置信度；
- 自动处理原因或进入确认的原因；
- 最终领域动作、no-op、拒绝或合并结果。

建议新增质量指标：

- 每百次新建中 24 小时内被 consolidate 的比例；
- 同一事项关联的平均会话数；
- 用户选择“不是同一事项”的误合并候选率；
- 完成后仍存在语义近重复开放项的比例；
- tool + extraction 双入口被同一 source fingerprint 吸收的比例；
- 标题歧义动作被安全拦截的次数。

## 九、典型场景与建议行为

| 场景 | 建议裁决 | 说明 |
|---|---|---|
| 同一 turn 的 `memory_write` 与 LLM 输出标题相同 | `LINK` | 一个事项，两条操作/来源证据 |
| 同一 turn 标题为近义改写 | `LINK` 或 `ASK` | 结合用户原话、完成条件和对象 |
| 另一会话再次说“周五发演示稿” | `LINK` | 新增关联会话，不重写首次来源 |
| 另一会话说“改成下周一发” | `UPDATE` | 原 id 改期，新会话作为 correction evidence |
| 已完成后说“其实还没发” | `REOPEN` | 纠正同一 occurrence |
| 已完成后说“下周再发一次周报” | `NEW_OCCURRENCE` | 新实例，关联前次但不合并 |
| 两个会话同时创建相同标题 | 幂等/事务吸收 | 只创建一次 |
| 两个会话同时创建语义近义标题 | resolver 后 `LINK/ASK` | 不靠最后写入获胜 |
| “准备发布”与“补发布测试” | `ATTACH_STEP` 或 `ASK` | 可能是父事项与步骤 |
| 两个项目都有“提交验收材料” | `CREATE` 两项 | owner scope、客户或交付物不同 |
| 用户快速记录后在工作会话重复交代 | `LINK` | manual origin 保留，增加 session evidence |
| 助手重试同一个 tool call | 幂等重放 | operation id 唯一 |
| 两个重复项一条完成、一条开放 | state-aware consolidate | 保留完成事实，规范项不应继续提醒 |
| 标题匹配到两个开放事项 | `ASK/409 candidates` | 禁止任选最近一条 |
| 跨工作区疑似同一发布事项 | `ASK` | 确认 owner scope，另一个只保留来源关联 |

## 十、建议实施顺序

### 阶段 0：证据审计与样本集

先从真实 SQLite、`extraction_log.raw/parsed`、events 与 session 元数据整理重复样本，不改变写入行为。
每个样本人工标注 `LINK/UPDATE/REOPEN/NEW_OCCURRENCE/CREATE/STEP/NOOP`。

### 阶段 1：输入幂等与多会话 evidence

先解决“同一次输入执行两次”和“一项只能有一个会话”的结构问题。此阶段不做语义自动合并，风险最低，
但能为后续判断提供证据。

### 阶段 2：候选召回与 shadow resolver

新 resolver 只记录裁决，不改变现有写入。对比当前系统与人工标签，重点测漏合并和误合并。

### 阶段 3：高置信 LINK/UPDATE

只开放确定性幂等、显式 id 和高置信同 scope 关联；歧义仍进入 ASK。观察稳定后再扩大自动处理范围。

### 阶段 4：状态感知 consolidate 与确认界面

加入 `merged_into_id`、终态冲突处理、撤销合并和“待确认整理”入口。不要在没有可撤销与审计前自动合并。

### 阶段 5：跨工作区与父事项/步骤

最后处理跨 scope owner 和计划层级，因为它们会同时影响权限、提醒归属、动作路由和界面信息架构。

## 十一、验收矩阵

至少需要覆盖以下确定性用例：

1. 同 session/turn 事件重放，todo 与事件均只出现一次；
2. 同一 tool call 重试，返回同一结果；
3. tool + extraction 同标题及近义标题，最终各只有一个规范事项；
4. 两个 session 并发复述同一事项，得到一个 todo、两条 session evidence；
5. 同一事项跨会话改期、开始、完成，始终操作同一 id；
6. 完成声明重复出现，不新建、不重复写完成事件；
7. 完成后的纠正走 reopen；明确的新周期走 new occurrence；
8. 同标题不同项目、客户、日期实例不误合并；
9. 多候选标题动作返回歧义，不改变任何一条；
10. 一开一终态重复可安全 consolidate，提醒、来源和历史一致；
11. merged 副本不能普通 reopen，撤销合并能恢复；
12. 跨工作区候选未经确认不自动改变 owner scope；
13. 助手计划未获用户授权时不创建顶层事项；
14. dashboard、SQLite、事件审计、来源会话列表与提醒结果一致。

真实对话测试还应覆盖口语、省略指代、改口、多意图、周期事项、跨会话并发和助手工具重试，不能只使用
标题完全相同的理想输入。

## 十二、需要评审的产品决定

### 决定 1：终态后的同名提及默认怎么处理

建议：有“再次/下周/下一轮”等新 occurrence 信号时创建新项；有“其实/撤销完成”等纠正信号时 reopen；
其余进入 ASK，不默认为新建。

### 决定 2：跨工作区事项由谁拥有

建议：一个规范事项只有一个 owner scope；其他工作区的会话只作为 evidence。改变 owner 或合并跨工作区记录
必须确认。

### 决定 3：助手是否可以自动创建事项

建议：只有直接用户消息包含明确记录/跟进授权时，助手才能自动提交；assistant 自己拆出的步骤只能提案或
挂到已有事项下。

### 决定 4：语义近重复是否自动合并

建议：不直接自动 consolidate。高置信只把**新的提及** LINK 到已有规范项；已经存在的两条数据库记录仍走
显式、可撤销的 consolidate。

### 决定 5：合并后历史如何呈现

建议：历史显示“记录 B 已并入事项 A”，不显示为“用户取消了 B”；A 展示所有关联来源，B 默认隐藏但可从
审计中查看。

## 十三、推荐的最小方向

如果只批准一轮最小改造，建议优先做三件事：

1. **输入幂等**：为用户消息、抽取候选和助手工具调用建立稳定 fingerprint；
2. **多会话 evidence**：一个 todo 可以关联多个 session/turn，后续提及不再丢失；
3. **状态与记录分离**：引入 merged/superseded 语义，停止用 cancelled 表示重复项被吸收。

这三项不会要求系统立即学会所有语义去重，却能先消除重放双写、来源丢失和合并后状态失真的结构性问题，
也为后续 resolver、待确认和跨工作区连续性提供稳定基础。
