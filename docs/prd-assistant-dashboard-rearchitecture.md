> 文档状态：评审稿 1.0

> 产品对象：dsh-yolo 助手看板、提醒处理、事项对话与信任反馈
> 原型基线：2026-08-23 已评审通过的「助手判断优先」交互原型
> 发布说明：本文不指定版本号，不构成发布、打标或上线授权

## 0. 文档定位

本文定义一次跨产品、交互、前端架构、数据契约和质量体系的完整重构，不是单纯的视觉换肤。

它回答以下问题：

1. 用户打开助手看板时，第一眼应该看到什么，为什么；
2. 如何把「助手知道的事项」转化为少量、可信、可处理的判断；
3. 如何在 340px 常驻侧栏与宽屏工作台之间保持同一套信息架构；
4. 如何让来源、判断依据、处理结果和助手学到的规则都可检查、可纠正、可撤销；
5. 前端重构需要哪些数据和 API 支撑，旧数据与旧交互如何平滑迁移；
6. 如何用自动化测试和真机走查证明重构没有破坏现有产品红线。

本文在本次重构范围内是需求与验收依据。现有 [产品设计文档](product-design.md) 仍记录面板 1.0 的产品基线；进入开发后，应将本 PRD 的已确认决策同步回产品设计、开发计划和路线图，避免出现多个相互冲突的事实源。

## 1. 背景与问题

### 1.1 产品已经具备的能力

当前产品已经能够：

- 从真实会话中抽取承诺、计划、目标、里程碑与跟踪规则；
- 在本地 SQLite 中保存事项、来源会话、状态变化和审计事件；
- 聚合所有已知工作区，并将每一行操作路由回所属工作区；
- 将提醒投递到 YOLO 自有线程和助手看板，不打扰工作会话；
- 支持快速记录、完成、撤销完成、推迟、再次提醒、取消、编辑、对话处理；
- 展示来源会话、今日台账、目标与里程碑；
- 在侧栏对话与全屏对话之间切换；
- 在面板打开时按需加载，在动作和手动刷新后更新，不进行面板内高频轮询。

这些能力证明了产品链路可用，但当前前端仍更像「把数据按功能摆出来」，没有充分体现产品最独特的价值：替用户持续整理承诺，在合适的时刻给出少量、可解释的判断，并让用户保有最终控制权。

### 1.2 当前体验的核心问题

#### P0：看板缺少清晰的第一任务

用户进入后同时面对通知、筛选、五个视图、快速记录、多个事项、目标、台账和对话。各模块都合理，但缺少明确的阅读顺序。用户仍要自己判断「现在最值得回应什么」。

#### P0：助手的“判断”与普通待办排序差异不够明确

逾期、优先级、截止时间和滞留状态都有展示，但没有形成稳定的判断结构。若只做一个“AI 排序”标签，容易与 Todoist、Reclaim 等产品的智能优先级同质化。

#### P0：信任闭环不完整

原型中的“助手会记住”如果只是泛化承诺，会制造新的不确定性：

- 到底记住了什么；
- 是改变了事项状态，还是改变了提醒规则；
- 作用于当前事项、当前工作区，还是所有相似事项；
- 如果判断错了，用户能否撤销或纠正。

因此，“助手记住了”必须对应真实、具体、可检查的状态变化，不能只是一句成功文案。

#### P1：340px 侧栏的信息密度与宽屏结构不能简单等比缩放

完整判断卡、五个一级视图、复杂筛选和多列信息在宽屏可用，在 340px 会挤压阅读空间。紧凑模式需要独立的优先级和渐进披露策略，而不是缩小字号。

#### P1：功能图标和文字层级不够明确

用户已明确反馈：通知、对话、刷新、主题等图标需要一眼可辨；文字不能依赖过小字号或过低对比度迫使用户集中注意力。陌生功能不能只依靠图标猜测。

#### P1：来源、原因、处理和学习尚未形成统一链路

当前页面分别有来源会话、提醒、任务操作和偏好数据，但用户难以把它们理解为一条连续的产品链路：

> 为什么现在出现 → 这件事来自哪里 → 我如何处理 → 助手因此改变了什么

本次重构需要让这条链路成为产品结构，而不是零散字段。

### 1.3 同类产品对比结论

本次重构不追求复制任一同类产品，而是吸收其成熟交互并保持产品差异：

| 对比对象 | 借鉴 | 本产品应形成的差异 |
|---|---|---|
| Things | 安静、克制、渐进披露 | 不只陈列任务，还解释为何此刻值得回应 |
| Todoist | 快速记录、键盘效率、成熟列表操作 | 来源于真实会话，并能回到语境继续讨论 |
| Linear | 一致的状态、快捷键、反馈和组件纪律 | 面向个人工作与生活，不引入工程项目管理负担 |
| Reclaim 等智能规划产品 | Relevant Now、风险信号、自动整理 | 不以自动排程为核心，而以来源证据、用户处理和可审计学习建立信任 |
| deepseek-harness 生态插件 | 宿主一致性、面板与会话协作 | 成为跨会话的助手表面，但绝不侵入工作会话 |

结论：本产品的壁垒不是“AI 帮你排了顺序”，而是「来自原始会话的承诺 + 可解释的此刻判断 + 可继续对话 + 可检查的处理学习」。

## 2. 产品定义

### 2.1 一句话定义

助手看板是一个面向个人工作与生活的「判断收件箱」：它持续整理用户在不同会话中说过的承诺，在合适的时刻解释为什么需要回应，并让用户完成、推迟、讨论、纠正或忽略。

“判断收件箱”是内部产品定义，不强制作为界面文案。界面主文案仍使用「助手看板」「助手判断」「管理工作与生活的助手」。

### 2.2 核心价值

- 用户不必再次解释背景；
- 用户不必每天手动整理所有会话中的承诺；
- 用户能快速看懂为什么某件事此刻出现；
- 用户能追溯来源并继续对话；
- 用户始终知道系统改变了什么，并能撤销。

### 2.3 产品边界

本产品负责：

- 记住用户明确表达的承诺、计划、目标和跟踪规则；
- 聚合、排序、解释和提醒；
- 记录处理结果并调整明确的跟踪信号；
- 提供对话入口帮助用户澄清和整理。

本产品不负责：

- 未经用户确认代替用户发送消息、提交代码、下单或执行外部业务操作；
- 以强制日程或自动排期取代用户判断；
- 把普通事实、兴趣爱好、人格画像或生活细节无限制写入“记忆”；
- 在工作会话中主动插入提醒或跟进；
- 为了表现品牌而添加与任务无关的视觉装饰。

### 2.4 视觉隐喻边界

项目口号中的“沿着轨道稳稳推进”只描述结果，不是视觉设计指令。本次重构禁止把轨迹线、铁轨、轨道、运行路线、节点地图、环形轨道或类似装饰作为主视觉语言。品牌识别来自稳定的行为结构、排版、组件和反馈，不来自字面化口号。

## 3. 目标与非目标

### 3.1 业务与体验目标

#### G1：三秒内理解当前状态

用户打开看板后，应在三秒内回答：

- 现在有没有一件需要我回应的事；
- 为什么是它；
- 我可以做什么。

#### G2：建立可解释、可纠正的助手判断

每个重点判断都必须能够追溯到真实数据，不允许生成无法验证的“影响项目进度”等空泛理由。

#### G3：缩短核心处理链路

从打开面板到完成、推迟或进入事项对话，常见路径不超过两次主要点击；键盘用户可以在不使用鼠标的情况下完成同等操作。

#### G4：让 340px 成为正式形态

常驻侧栏不是宽屏页面的降级版本。它应保留核心判断、处理、来源和对话能力，同时通过折叠和二级入口控制密度。

#### G5：形成可验证的学习回执

任何“助手记住”提示都必须关联实际写入的事项、偏好、计数或规则；能够查看作用范围，并在可逆场景中撤销。

#### G6：保持宿主一致与产品克制

使用宿主熟悉的面板、按钮、菜单、焦点和主题行为；建立明确识别度，但不做独立桌面应用式的重装饰。

### 3.2 建议衡量指标

指标默认本地统计，不上传个人内容；若未来需要遥测，必须另行获得明确授权并进行脱敏设计。

| 指标 | 定义 | 首版目标 |
|---|---|---|
| 首个有效处理时间 | 打开看板到完成/推迟/对话/忽略之一 | 中位数较现状降低 30% |
| 判断卡处理率 | 被展示的重点判断在 24 小时内获得明确处理的比例 | ≥ 60% |
| 来源查看率 | 用户打开来源会话或来源摘录的比例 | 观察项，不设越高越好 |
| 判断纠正率 | 用户选择“不再这样提醒/原因不对/编辑”的比例 | 作为质量信号，持续下降但不得隐藏入口 |
| 撤销成功率 | 发起撤销后正确恢复的比例 | 100% |
| 误导性学习回执 | 文案称已学习但没有对应持久化记录 | 0 |
| 工作会话提醒注入 | 提醒主动进入非 YOLO 工作会话的次数 | 0 |
| 键盘阻断缺陷 | 核心流程不能由键盘完成的 P0/P1 缺陷 | 0 |

指标不是发布授权条件；发布准入以第 17 节验收标准为准。

### 3.3 非目标

本次不实现：

- 日历时间块自动排程；
- 多人协作、任务指派和权限系统；
- 云端同步或跨设备账号系统；
- 独立移动 App；
- 通用项目管理中的看板列、甘特图、工时与报表；
- 自动执行事项内容；
- 重新命名代码中的 YOLO 内部标识。

## 4. 用户与核心任务

### 4.1 主要用户

同时在多个 dsh 会话、多个工作区处理研发、沟通和生活安排，希望助手记住承诺，但不希望被频繁打断或把管理本身变成额外工作的用户。

### 4.2 核心用户任务（JTBD）

#### JTBD-1：快速知道现在该回应什么

当我在不同会话间切换或重新开始一天时，我希望助手告诉我此刻最值得回应的一件事及原因，以免重新浏览所有对话和列表。

#### JTBD-2：在不丢失语境的情况下处理事项

当一项任务看起来不清楚或需要权衡时，我希望直接看到来源，并围绕该事项开始一段干净的新对话。

#### JTBD-3：快速给出明确处理结果

当我已知道答案时，我希望直接完成、推迟、再次提醒或取消，而不是进入复杂编辑表单。

#### JTBD-4：确认助手到底记住了什么

当助手说它会调整提醒时，我希望看到具体规则、作用范围和撤销入口，以防错误逐渐累积。

#### JTBD-5：回顾今天发生了什么

当我结束一天或追查状态变化时，我希望看到按真实时间排序的变更，以及每个变更来自会话、助手还是手动操作。

## 5. 产品原则

### 5.1 判断优先，列表在后

有明确需要回应的事项时，页面第一视觉焦点只能有一个“助手判断”。其余事项是支持性列表，不与重点卡竞争。

### 5.2 证据先于结论

所有“为什么现在”必须由可验证信号组成，例如：

- 已逾期 1 天；
- 距离截止不到 2 小时；
- 已推迟 2 次；
- 8 天未更新；
- 关联目标仍处于进行中；
- 刚收到一条未处理提醒。

不得仅显示“很重要”“可能影响进度”而不给出依据。影响描述只能在有明确关联数据时出现。

### 5.3 先处理，再编辑

处理面板先提供完成、推迟、再次提醒、讨论等用户意图，再提供标题、截止时间、优先级、里程碑等字段编辑。

### 5.4 完整首读，紧凑复读

同一重点判断第一次看到时展示完整原因、来源和处理选项；用户看过但未处理后，再次打开默认展示紧凑状态，避免每次占据过多空间。用户可重新展开完整内容。

### 5.5 一次只承诺一种学习

成功反馈必须区分：

- 已改变事项状态；
- 已改变本次提醒时间；
- 已记录一个提醒偏好；
- 仅记录了本次选择作为质量计数。

不能把上述动作统称为“助手已经学会”。

### 5.6 渐进披露，不牺牲可发现性

高级筛选、目标、台账、刷新、主题进入二级入口；但入口必须有清晰文字、标准图标和可访问名称，不能变成难以发现的无标签图标。

### 5.7 管理而非代办

界面动词使用“记录、提醒、讨论、整理、更新、完成、推迟、取消”，避免暗示助手已经替用户执行外部工作。

### 5.8 本地、安静、可逆

个人内容本地保存；提醒只进入 YOLO 表面；重要状态变化有审计；可逆动作提供明确撤销。

## 6. 信息架构

### 6.1 产品表面

助手看板由五个表面组成：

1. 宿主侧栏入口：打开看板、显示轻量未处理角标；
2. 看板主表面：判断、建议事项、今天事项和收束；
3. 事项处理面板：查看依据、快速处理和编辑；
4. 对话表面：全局对话或围绕事项的新对话，支持侧栏与全屏；
5. 辅助视图：即将、已完成、目标、台账、筛选和设置。

### 6.2 一级导航

在 340px 常驻侧栏中，一级视图只保留：

- 今天；
- 即将；
- 已完成。

目标与台账放入“更多”菜单或页面内上下文入口：

- “今天进展”进入台账；
- 事项的目标信息进入目标详情；
- 更多菜单提供“目标与里程碑”“今日台账”。

在宽屏模式下，可根据可用宽度展示完整五项导航，但顺序和语义必须与紧凑模式一致，不能形成两套产品。

### 6.3 顶部操作层级

从高到低：

1. 对话：主要按钮，使用明确的对话气泡图标和“对话”文字；
2. 通知：次级按钮，使用标准铃铛图标、未处理数量和“通知”文字；
3. 更多：包含刷新、主题、目标、台账及低频设置；
4. 关闭：标准关闭图标，固定在可预测位置。

筛选属于事项列表，不放在产品全局工具组中。列表出现时，筛选入口位于列表标题或列表工具行。

### 6.4 “今天”页面阅读顺序

1. 日期、页面标题与一句简短说明；
2. 快速记录；
3. 助手判断（若存在）；
4. 需要关注；
5. 今天；
6. 今天进展；
7. 收束建议（达到展示条件时）。

同一事项不得同时出现在“助手判断”和下方列表。重点卡退出后，事项根据当前状态回到对应列表。

## 7. 核心页面需求

### 7.1 看板头部

#### 结构

- 产品标识：YOLO 助手或宿主约定名称；
- 当前页面：今天/即将/已完成；
- 对话按钮；
- 通知按钮；
- 更多菜单；
- 关闭按钮。

#### 规则

- 通知、对话、刷新、主题必须使用行业通用轮廓图标；
- 对话和通知保留可见文字，不使用只有图标的陌生按钮；
- 刷新和主题在更多菜单中同时显示图标与完整文字，例如“刷新看板”“切换为深色主题”；
- 未处理数量是通知按钮的一部分，读屏名称为“通知，2 条未处理”；
- 所有按钮最小点击区域 36×36px，紧凑模式不低于 32×32px；
- 禁止用表情符号作为功能图标；
- 状态不能只靠颜色表达。

### 7.2 快速记录

#### 主流程

- 输入一句事项，回车保存；
- 默认今天到期；
- Shift+Enter 不提交；输入法组合过程中 Enter 不误提交；
- 保存成功后输入框清空，事项进入“今天”；
- 成功提示为“已记下 · 默认今天到期”，并提供“编辑”入口；
- 重复事项由服务端既有去重规则处理，客户端不伪造成功。

#### 扩展建议

后续可支持自然语言日期，但本次重构不得让 LLM 成为快速记录的必经路径。快速记录继续直接写入，以保持确定性和低延迟。

### 7.3 助手判断组件

助手判断是本产品的标识性组件，识别度来自固定结构和行为，不依赖大面积渐变或装饰图形。

#### 完整状态结构

1. 状态头：助手判断 / 需要你回应 / 出现时间；
2. 事项标题；
3. 为什么现在：一句结论 + 最多三条证据；
4. 来源：会话摘要、工作区和可选摘录；
5. 主操作：完成、推迟、讨论；
6. 次操作：更多处理、暂时忽略、原因不对；
7. 处理后影响预告：仅描述真实会发生的状态变化。

#### 紧凑状态结构

1. 助手判断标识；
2. 事项标题；
3. 一条最强原因；
4. 主处理按钮；
5. “展开依据”。

#### 展示规则

- 同时最多一个；
- 必须达到判断阈值，不能为了保持版式而强行选一项；
- 已完成、已取消或已处理通知不得继续展示；
- 用户首次看到后记录 `seen_at`，但“已看”不等于“已处理”；
- 同一判断在证据未变化时维持稳定，不因每次刷新随机换项；
- 证据、截止时间或状态变化后可重新生成判断版本；
- 工作区聚合失败时，不得声称这是全局最重要事项，应显示“部分工作区暂不可用”。

### 7.4 需要关注列表

用于展示重点卡之外值得注意的事项。

每行包含：

- 完成控件；
- 标题；
- 一个短原因标签，如“逾期”“2 小时内”“8 天未动”；
- 一行短解释；
- 来源会话或“快速记一条”；
- 到期时间；
- 单一“处理”按钮。

规则：

- 行内不平铺完成、明天、编辑、讨论等多个同权按钮；
- 点击“处理”打开事项处理面板；
- 点击来源进入原会话并关闭覆盖面板；
- 点击标题可选中行，但不得误触完成；
- 键盘聚焦行时 Enter 打开处理面板，Space 只在完成控件上改变状态；
- 行内只显示短原因，完整依据进入处理面板，避免重复“为什么现在”造成模板感。

### 7.5 今天列表

展示今天到期但未进入“需要关注”的普通事项。视觉权重低于需要关注列表。

- 默认按到期时间升序，再按优先级、更新时间、稳定 id 排序；
- 无明确时间的“今天”事项排在有时间事项之后；
- 完成后立即从开放列表退出；
- 显示 4 秒撤销提示；
- 撤销使用服务端 `reopen` 领域动作，不只做客户端回滚；
- 取消事项不计入“已完成”，在已完成视图中应明确区分或默认隐藏。

### 7.6 今天进展与收束

“今天进展”默认是一行紧凑摘要，例如：

> 已完成 7 项 · 变更 12 条 · 来自 4 个会话

点击后进入今日台账。

满足以下任一条件时展示收束卡：

- 当天有已完成事项且仍有高风险未处理事项；
- 当天有多次状态变更，适合回顾；
- 用户接近安静时段开始时间。

收束卡提供：

- 回顾变更；
- 和助手收束。

收束是建议，不得产生持续催促；用户关闭后当天不再次自动出现，除非状态发生实质变化。

### 7.7 即将

展示未来 7 天到期事项与滞留事项，区分：

- 明天；
- 本周；
- 更晚；
- 无日期但滞留。

不得把“滞留”伪装为精确截止。筛选可改变时段、状态、里程碑和关键词。

### 7.8 已完成

- 默认只展示 done/completed；
- cancelled 使用单独筛选“已取消”，不能混入完成计数；
- 展示完成时间和来源；
- 支持重新打开；
- 重新打开后回到所属日期/关注桶，并留下审计事件。

### 7.9 目标与里程碑

- 作为二级视图，不与今日处理争夺一级导航；
- 显示状态、进展和关联事项；
- 进展来源必须标注为“来自对话陈述”或相应数据来源；
- 如果进展不可手动修改，界面明确说明；若允许修改，必须走统一领域动作并审计；
- 目标废弃、里程碑状态变更等危险操作需要确认或可撤销反馈。

### 7.10 今日台账

- 按全局真实时间倒序，不按工作区分组破坏时间顺序；
- 每行包含时间、事件类型、摘要、来源和工作区；
- 来源会话可点击跳回；
- 快速记录、助手操作、看板操作和早期记录使用不同文字标签，但不能只靠颜色区分；
- 拒绝的动作可在调试/高级筛选中查看，普通用户默认不被错误日志淹没；
- 工作区部分读取失败时明确显示缺失范围。

## 8. 事项处理面板

### 8.1 打开方式

- 点击事项行“处理”；
- 键盘选中事项后按 Enter；
- 从通知或助手判断进入；
- 从事项对话返回。

### 8.2 信息顺序

处理面板按以下顺序展示：

1. 事项标题与所属工作区；
2. 判断依据；
3. 来源会话摘要与可选摘录；
4. 快速处理；
5. 助手将记录的变化；
6. 编辑字段；
7. 危险操作。

传统表单字段不能排在判断依据之前。

### 8.3 快速处理

首屏至少提供：

- 标记完成；
- 推迟到明天；
- 和助手讨论。

二级操作：

- 选择其他日期/时间；
- 再提醒一次；
- 暂时忽略本次判断；
- 取消事项；
- 原因不对。

“推迟到明天”必须使用本地时区解析为绝对日期并在请求中传递，不由服务端猜测相对日期。

### 8.4 编辑字段

- 标题；
- 截止日期与时间；
- 优先级；
- 里程碑；
- 备注/上下文。

字段保存走统一 `POST /yolo/actions`，不能直接操作本地 React 状态后伪装成功。

### 8.5 原因不对

用户选择“原因不对”后，提供轻量原因：

- 时间判断不对；
- 这件事已不重要；
- 不应关联这个目标；
- 不要再因“长期未动”提醒；
- 其他。

处理规则：

- 反馈本身不自动取消事项；
- 能映射到明确规则时，展示待确认的偏好变更；
- 不能映射时，仅记录本次判断质量反馈，不声称已经学会；
- 用户可选择编辑事项、忽略本次或取消事项。

## 9. 对话需求

### 9.1 两类对话

#### 全局对话

- 从头部“对话”进入；
- 使用当前工作区对应的 YOLO 常驻线程；
- 用于回顾、整理、澄清整体计划；
- 历史可恢复。

#### 事项对话

- 从助手判断、事项行或处理面板进入；
- 每次打开创建全新的临时 `yolo-a-*` 线程；
- 不继承常驻对话历史；
- 将事项标题、id、所属工作区和必要上下文作为受控锚点传入；
- 收到真实模型回复前显示明确的发送/等待状态；
- 关闭或切换事项后，本次临时线程不再复用。

### 9.2 形态

- 宽屏：340px 侧栏对话，可展开全屏；
- 面板可用宽度低于 480px：直接使用全屏对话；
- Esc 顺序：关闭菜单 → 退出全屏对话 → 关闭侧栏对话/处理面板 → 关闭看板；
- 切换宿主会话时关闭看板，防止面板遮挡且语境错位；
- 全屏与侧栏切换时，看板内部草稿、折叠状态和撤销窗口不能因组件卸载丢失。

### 9.3 对话后的状态同步

若对话通过 `yolo_action` 改变事项：

- 面板收到成功结果后刷新看板；
- 临时对话保留简短确认；
- 事项从当前列表迁移到正确状态；
- 台账记录来源会话；
- 若动作产生可检查的偏好变化，显示学习回执。

## 10. 判断与排序规则

### 10.1 设计目标

排序必须稳定、可解释、可测试。首版以确定性规则为事实源，LLM 只允许润色已有证据，不得生成新事实，也不得改变候选资格和排序结果。

### 10.2 候选门槛

只有开放事项可成为判断候选。满足以下任一条件时进入候选集：

- 存在关联的未处理提醒；
- 已逾期；
- 距离明确截止时间不超过 24 小时；
- 优先级为 urgent 且 72 小时内到期；
- 超过 7 天未更新；
- 在可用审计数据中发现连续推迟至少 2 次；
- 关联进行中的里程碑且该事项是近期唯一未完成项。

### 10.3 建议评分

首版评分用于排序，不直接展示数值：

| 信号 | 分值建议 |
|---|---:|
| 未处理到期提醒 | +50 |
| 已逾期 | +40 + 每逾期一天最多 +20 |
| 2 小时内到期 | +35 |
| 24 小时内到期 | +20 |
| urgent / high | +20 / +10 |
| 连续推迟至少 2 次 | +15 |
| 7 天以上未更新 | +10 |
| 关联活跃目标或里程碑 | +5 |
| 用户当日已明确忽略该判断 | -100 |

同分时依次按：最早到期、最高优先级、最早更新时间、稳定 id 排序。

该表是产品默认，不要求硬编码在 UI；实现时应集中在可测试的领域函数中，禁止散落在组件条件判断里。

### 10.4 判断版本与稳定性

每个判断由以下指纹确定：

- 事项 id；
- 状态；
- 截止时间；
- 优先级；
- 提醒 id/状态；
- 推迟次数；
- 更新时间；
- 目标/里程碑关联状态；
- 排序规则版本。

指纹不变时刷新不得随机改变原因或候选顺序。规则升级时记录 `reason_version`，便于测试和问题追踪。

### 10.5 原因文案层级

- 助手判断完整卡：一句结论 + 1–3 条证据；
- 事项列表：一条短原因；
- 处理面板：完整证据与来源；
- 通知：只给用户可读的提醒正文，不携带 agent 操作规则。

## 11. 信任、学习与撤销

### 11.1 学习回执模型

每次动作成功后，服务端可返回 `learning_receipt`。回执必须属于以下类型之一：

| 类型 | 用户文案示例 | 实际写入 |
|---|---|---|
| `state_change` | 已标记完成 | todo 状态 + 审计事件 |
| `schedule_change` | 已推迟到 8 月 24 日 | due_at + 审计事件 |
| `reminder_reset` | 已允许再次提醒 | last_reminded_at + 审计事件 |
| `feedback_count` | 已记录你取消了这项跟踪 | good/stale 计数 + 审计事件 |
| `preference_change` | 已将此类提醒改为工作日上午 | preference + 历史记录 |
| `no_learning` | 已处理；未改变提醒偏好 | 仅业务状态变化 |

客户端只能根据服务端回执显示上述文案，不得自行推断“助手记住了”。

### 11.2 可查看内容

学习回执展开后显示：

- 改变的字段或规则；
- 旧值与新值；
- 作用范围：本事项 / 本工作区 / 所有工作区；
- 来源动作与时间；
- 撤销入口；
- “查看提醒偏好”入口。

### 11.3 偏好变更确认

从单次行为推导长期提醒偏好时，默认采用“建议确认”，不能静默写入。例如：

> 你连续三次把晚间提醒推到次日上午。以后将此类提醒安排在工作日上午？

只有用户明确确认后才写入长期偏好。单次完成或推迟只更新事项，不自动推导跨事项规则。

### 11.4 撤销

- 完成 → `reopen`；
- 推迟 → 恢复旧 `due_at`；
- 偏好变更 → 从 `preference_history` 恢复上一有效值；
- 通知已处理 → 如产品需要恢复，必须有独立领域动作，不能直接改客户端角标；
- 取消 → 首版可要求在“已取消”中恢复，若不能安全撤销需提前明确提示。

撤销请求继续通过统一动作通路并留下审计，不能直接写数据库。

### 11.5 数据最小化

- 来源摘录只保存/返回解释当前事项所需的最短片段；
- 默认不在聚合看板暴露完整会话正文；
- 跳回来源会话优先于复制长文本；
- 工作区绝对路径只用于本地路由，用户界面显示友好名称；
- 不把普通人格或生活细节包装为提醒偏好。

## 12. 状态机与交互契约

### 12.1 判断展示状态机

```text
eligible
  └─ first_render → full_unseen
       ├─ seen → compact_seen
       ├─ open → handling
       └─ ignore_today → suppressed_today

compact_seen
  ├─ expand → full_seen
  ├─ open → handling
  └─ evidence_changed → full_unseen(new version)

handling
  ├─ action_pending → success | error
  ├─ chat → anchored_chat
  └─ close → previous display state

success
  ├─ undo_available → undone
  └─ terminal/settled → removed from attention
```

“已看”“已处理”“忽略本次”必须是不同状态。

### 12.2 事项状态机

沿用领域状态：

```text
pending → in_progress → done
   │           │          │
   ├───────────┴→ cancelled
   ├─ postpone ─→ pending (due_at changed)
   ├─ remind_again → pending (reminder eligibility reset)
   └←──────── reopen ←──── done
```

每次状态迁移必须：

- 服务端校验；
- 写入审计事件；
- 清理或更新关联通知；
- 返回最新 item；
- 在跨工作区场景按 `scope_cwd` 路由。

### 12.3 加载状态

- 首次加载：结构化骨架屏，保持页面框架稳定；
- 手动刷新：保留旧数据，局部显示刷新状态，不整页闪白；
- 动作提交：只锁定相关按钮，防止重复提交；
- 加载失败且无旧数据：错误页 + 重试；
- 加载失败但有旧数据：保留旧数据并显示“刷新失败，内容可能不是最新”；
- 部分工作区失败：保留成功数据并显示可展开的失败工作区列表；
- 空态：明确“今天没有挂起的事”，保留快速记录和对话入口。

### 12.4 乐观更新

仅允许对可逆、结果确定的动作做受控乐观反馈。服务端失败时必须回滚并解释失败原因。跨工作区动作默认等待服务端确认后迁移行，避免错误作用域造成假成功。

### 12.5 Toast 与反馈

- 成功 toast 默认 4 秒；
- 可撤销动作包含键盘可聚焦的“撤销”；
- 错误 toast 使用 `role="alert"`；
- 普通成功反馈使用 `role="status"`；
- 静态提示不得永远占据页面；
- 文案说清结果，不使用“操作成功”这类无信息反馈。

## 13. 数据与 API 需求

### 13.1 兼容原则

- 继续以 `GET /yolo/dashboard?scope=all` 作为聚合读取入口；
- 继续以 `POST /yolo/actions` 作为所有状态变化的统一入口；
- 新字段优先做向后兼容的可选字段；
- 新动作由共享类型、服务端校验、模型工具和客户端共同使用同一契约；
- 不允许客户端直接拼接数据库状态；
- 不重新引入“当前工作区/全部工作区”切换，看板始终聚合所有已知工作区。

### 13.2 Dashboard v2 建议扩展

| action | kind | 用途 |

| `suppress` | attention | 忽略本次或忽略到某时刻 |
| `feedback` | attention | 记录“原因不对”及分类 |
| `update` | preference | 用户确认修改提醒偏好 |
| `invalidate` | preference | 停用错误偏好 |
| `restore` | preference | 从历史恢复偏好 |
| `reopen` | todo | 沿用已有撤销完成动作 |

其中 `attention` 可以是派生实体，不一定需要独立持久化表；但 `seen/suppress/feedback` 至少要有稳定存储，不能只存在浏览器内存。

### 13.7 存储变更建议

优先采用增量迁移：

1. `attention_feedback`：事项、判断版本、seen/suppressed/feedback、时间与作用域；
2. todo 增加或从事件派生 `postpone_count`；
3. preference 保持现有 history，补充用户确认来源和可逆审计；
4. source excerpt 如需持久化，单独做最小长度字段并明确保留策略；
5. 所有迁移使用 schema version，启动时幂等执行；
6. 旧数据缺少来源或判断反馈时使用安全回退，不批量伪造历史。

### 13.8 刷新与轮询

- 打开看板：加载一次；
- 完成动作：刷新或应用服务端返回的新 projection；
- 手动刷新：重新加载；
- 面板打开期间：不恢复 30 秒全量轮询；
- 侧栏角标：继续使用独立轻量轮询；
- 若未来增加推送，必须保证断线后可回退到手动刷新，且不改变安静原则。

## 14. 视觉与设计系统要求

### 14.1 整体气质

- 现代、克制、明确；
- 以排版、间距、结构线和状态反馈建立高级感；
- 中性色 + 单一 indigo 强调色，功能状态色总数控制在必要范围；
- 不使用大面积高饱和渐变、玻璃拟态、发光、拟物仪表盘或装饰插画；
- 发丝线用于分组，不把页面切成大量厚重卡片；
- 助手判断可以是唯一具有更强边界和强调的组件。

### 14.2 字体与可读性

建议最低规格：

| 元素 | 最小字号 | 最低要求 |
|---|---:|---|
| 页面标题 | 28px 宽屏 / 24px 紧凑 | 600–700 字重 |
| 分区标题 | 15px | 600 字重 |
| 事项标题 | 15px | 550–600 字重 |
| 正文/说明 | 14px | 正文对比度达到 WCAG AA |
| 元数据 | 12px | 只用于时间、来源等辅助信息，不能承载关键动作 |
| 按钮文字 | 13–14px | 不使用低于 12px 的关键按钮文字 |

禁止通过过低透明度制造“高级感”。重要说明、按钮、原因、到期时间和来源必须在普通办公显示器上无需刻意凝视即可阅读。

### 14.3 图标

- 使用统一 SVG 线性图标库；
- 线宽、端点、视图框和视觉尺寸统一；
- 通知=铃铛，对话=带文本线的气泡，刷新=环形箭头，主题=半明半暗圆形或日/月标准符号；
- 图标与文字间距稳定；
- 图标不单独承担非通用语义；
- 每个图标按钮都有 `aria-label` 和 tooltip；
- 活跃、未处理、禁用状态不能只通过图标颜色区分。

### 14.4 组件层级

按钮分为：

- Primary：当前最主要的单一动作，如“处理”“和助手讨论”；
- Secondary：完成、推迟、对话等并列意图；
- Quiet：回顾、筛选、更多；
- Icon：关闭、展开等行业通用动作。

同一局部区域最多一个 Primary。

### 14.5 动效

- 常规状态变化 120–180ms，最长不超过 200ms；
- 只使用淡入、位移 2–4px、颜色和高度过渡；
- 不使用持续扫光、循环呼吸、轨迹动画；
- 数据更新不让整个页面闪烁；
- `prefers-reduced-motion: reduce` 时关闭非必要动画。

### 14.6 明暗主题

- 跟随宿主主题为默认；
- 用户手动切换时说明目标主题，不只写“主题”；
- 两种主题均满足正文、辅助文字、边框、状态色对比度；
- 颜色 token 统一，不在组件内硬编码渐变和十六进制颜色；
- 深色主题避免纯黑大面积背景和高亮白线造成刺眼。

## 15. 响应式与布局

### 15.1 布局档位

| 可用宽度 | 形态 | 核心规则 |
|---:|---|---|
| ≥ 960px | 宽屏工作台 | 主列表 + 340px 对话/处理侧栏可并列 |
| 480–959px | 中等面板 | 单列看板，处理面板覆盖或抽屉；对话可全屏 |
| < 480px | 紧凑模式 | 按 340px 正式设计；对话和处理使用全屏 |

### 15.2 340px 紧凑模式

- 一级视图只显示今天、即将、已完成；
- 助手判断默认采用紧凑复读结构；首次未读可完整展示，但首屏必须露出主操作；
- 不缩小关键文字换空间；
- 来源与原因允许换行，禁止横向滚动；
- 列表行从左右结构改为上下信息结构，处理按钮仍保持可见；
- 顶部对话、通知可以采用图标+短文字；刷新、主题进入更多；
- 处理面板和对话全屏打开；
- 安全区域、滚动容器和固定按钮不能互相遮挡。

### 15.3 宽屏模式

- 内容列设置最大阅读宽度，避免事项行横跨整个显示器；
- 对话/处理侧栏固定为约 340px，可根据宿主空间小幅调整；
- 五个视图可展开，但今日、即将、已完成仍保持主顺序；
- 重点判断不因宽度增加而堆入更多装饰或额外指标。

## 16. 可访问性与键盘

### 16.1 基线

目标达到 WCAG 2.1 AA 的可操作标准，至少覆盖：

- 正文 4.5:1 对比度；
- 大文字与非文本控件 3:1；
- 可见焦点；
- 完整键盘操作；
- 正确语义和读屏名称；
- 减少动效支持；
- 不只用颜色表达状态。

### 16.2 键盘模型

- Tab：按视觉顺序移动；
- Enter：打开选中事项或执行按钮；
- Space：仅在按钮、checkbox 等控件上执行，不由整行劫持；
- Esc：按最内层表面逐级关闭；
- 视图标签：支持 Left/Right 切换、Home/End 到首尾，并维护 `aria-controls`；
- 菜单：打开后焦点进入菜单，关闭后回到触发按钮；
- 对话发送：Enter 发送，Shift+Enter 换行，输入法组合不误发；
- 撤销：toast 内按钮可聚焦，不因自动消失抢走焦点。

### 16.3 焦点恢复

- 处理面板关闭后回到原“处理”按钮；
- 对话关闭后回到打开对话的事项或头部按钮；
- 来源跳转关闭看板，由宿主负责聚焦目标会话；
- 行因完成而移除时，焦点移动到下一项或分区标题并通过 live region 说明变化。

## 17. 验收标准

### 17.1 产品验收

#### PRD-A1：唯一重点判断

- 有合格候选时只展示一个助手判断；
- 重点事项不在下方重复；
- 无合格候选时不展示空壳判断卡。

#### PRD-A2：解释可核验

- 原因中的时间、次数、目标状态均可从 payload 或审计事件验证；
- 没有证据时使用保守回退文案，不生成推测性影响；
- 列表短原因与处理面板完整原因一致。

#### PRD-A3：来源闭环

- 有 session id 的事项能显示来源摘要并跳回原会话；
- 手动、工具、旧数据使用明确回退标签；
- 跨工作区来源和动作均使用该行所属 `scope_cwd`。

#### PRD-A4：处理闭环

- 完成、推迟、再次提醒、取消、编辑、重新打开均走统一领域动作；
- 服务端失败不产生假成功；
- 成功后行进入正确分区，通知和角标同步更新。

#### PRD-A5：学习可信

- 每一条“记住/调整偏好”文案都有服务端 `learning_receipt`；
- 能查看变化内容和作用范围；
- 可逆变化可撤销；
- 未改变偏好时明确写“未改变提醒偏好”。

#### PRD-A6：对话隔离

- 全局对话使用常驻线程；
- 每次事项对话是干净的新线程，不继承常驻历史；
- 事项动作在对话完成后同步回看板；
- 任何提醒不主动进入工作会话。

#### PRD-A7：聚合一致性

- 看板始终聚合所有已知工作区；
- 行携带工作区归属；
- 部分工作区失败不会让整页不可用，也不会隐藏“部分数据”提示；
- 台账保持全局时间顺序。

### 17.2 视觉验收

- 340px、480px、960px、1440px 无横向滚动；
- 关键正文和按钮不低于第 14.2 节规格；
- 通知、对话、刷新、主题图标无需猜测；
- 陌生图标有文字或 tooltip；
- 明暗主题均通过对比度检查；
- 页面不出现轨迹、轨道、路线图式装饰；
- 助手判断在不依赖大面积色块的情况下仍是第一视觉焦点；
- 动效不超过 200ms，减少动效模式无非必要动画。

### 17.3 性能验收

在约 10 个工作区、2,000 条开放/历史事项的参考数据集上：

- 聚合 dashboard API 本机 p95 目标 ≤ 500ms；
- 已有缓存/数据返回后，首个可读内容目标 ≤ 1.5s；
- 输入、菜单和行选择反馈在主线程无明显卡顿，交互反馈目标 < 100ms；
- 列表超过 200 行时评估窗口化或分段加载，不能一次渲染导致明显冻结；
- 动作提交期间不阻塞其他只读区域。

若现有基线无法达到，应在开发第一阶段记录基线并确认可接受增量，不能通过隐藏加载状态规避。

### 17.4 可靠性验收

- 重复点击同一动作不会产生重复审计或错误状态；
- 网络/服务端失败后可重试；
- 旧数据库迁移幂等，重复启动不破坏数据；
- 未知 `scope_cwd` 被拒绝并留下审计；
- 客户端刷新不丢失未保存编辑草稿、折叠状态和有效撤销窗口；
- 面板打开期间不进行 30 秒全量轮询；
- 侧栏角标轮询不读取完整 dashboard。

### 17.5 现有真机 W1–W10 回归

实现必须继续覆盖 [测试文档](testing.md) 中的 W1–W10，并将本 PRD 新增场景扩展为：

- W11：助手判断完整首读 → 紧凑复读 → 依据变化后重新完整展示；
- W12：学习回执可查看、偏好确认与撤销；
- W13：部分工作区失败时的提示与动作安全；
- W14：通知/对话/刷新/主题图标与读屏名称；
- W15：取消项不计入已完成、重新打开迁移正确；
- W16：判断原因与 evidence payload 一致，不出现无依据文本。

### 19.2 状态分层

toast、撤销倒计时、临时高亮。

- 先建立 token 和基础组件，再迁移页面；
- 禁止新旧按钮样式长期混用；
- 图标统一替换时建立语义映射表和快照测试；
- 删除无引用样式前使用 `rg` 和构建产物确认；
- 保留宿主主题探测与边界，不覆盖宿主全局 CSS。

建议在重构周期使用内部功能开关：

- 默认开发环境可开启 v2；
- 旧 UI 与 v2 读取同一领域数据，不进行两套业务写入；
- 出现 P0 时可回退旧 UI，而新增 schema 保持向后兼容；
- 功能稳定后删除开关和旧实现，避免永久双维护。

### 20.4 数据迁移回退

- 新表和新列不破坏旧查询；
- 回退 UI 时保留新反馈数据，不删除；
- schema migration 不提供自动降级删除；
- 若必须回滚二进制，旧版本应忽略新表/新列继续工作；
- 任何物理删除或不可逆清理需单独评审。

## 21. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| “助手判断”原因质量空泛 | 品牌组件失去信任 | 确定性 evidence 为事实源；无证据不生成影响描述 |
| 判断卡过高 | 340px 首屏被占满 | 完整首读/紧凑复读；主操作首屏可见 |
| “助手记住”成为虚假承诺 | 长期信任损失 | 服务端 learning receipt；无回执不得显示学习文案 |
| 五视图拥挤 | 紧凑模式不可用 | 只保留今天/即将/已完成一级导航 |
| 重构同时改变过多领域 | 缺陷难定位 | 按 Phase 和逻辑检查点提交；契约先行 |
| 跨工作区误操作 | 修改错误数据 | scope 白名单、行归属、服务端路由、E2E |
| LLM 生成不稳定 | 刷新后原因变化 | 指纹、规则版本、LLM 仅润色证据 |
| 旧数据缺来源 | 页面出现空洞 | legacy/manual 回退标签，不伪造来源 |
| 对话线程混用 | 泄露无关语境 | 全局常驻与事项临时线程严格分离 |
| 新 UI 性能下降 | 聚合场景卡顿 | 基线、服务端排序、渐进加载、性能门槛 |
| 设计追求“高级”导致过淡 | 可读性下降 | 最小字号、AA 对比度、真机普通屏验证 |

## 23. 默认产品决策

为避免开发阶段反复等待选择，本文给出以下默认决策；如评审未提出异议，即按此实现：

1. 产品表面称“助手看板”，标识组件称“助手判断”；
2. 看板始终聚合所有已知工作区；
3. 340px 一级导航为今天/即将/已完成；
4. 目标和台账进入更多或上下文入口；
5. 同时最多一个重点判断；
6. 判断排序由确定性服务端规则决定；
7. LLM 不决定候选、不修改 score，只可润色已给 evidence；
8. 首次完整、复读紧凑；
9. 单次操作不自动生成长期偏好，长期偏好需确认；
10. 客户端没有 learning receipt 时不显示“助手记住了”；
11. 快速记录继续无 LLM 直写；
12. 对话为头部主操作，通知为次操作，刷新和主题进入更多；
13. 完成保留 4 秒撤销；
14. 动效不超过 200ms；
15. 不使用轨迹、轨道或路线隐喻；
16. 不在本 PRD 中决定版本号、发布时间或发布渠道。
